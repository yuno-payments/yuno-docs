## Atributos del webhook {#webhook-attributes}

A continuación se listan los atributos JSON de los webhooks de Yuno. Consulta [Events and Triggers](/es/docs/webhooks/events) para ver el campo trigger que selecciona cada evento.

<ParamField body="account_id" type="string">
   El identificador único de la cuenta en Yuno (MAX 64, MIN 36).
</ParamField>

<ParamField body="type" type="string">
  Especifica el tipo de notificación.
</ParamField>

<ParamField body="type_event" type="string">
  Especifica el tipo de notificación del evento.
</ParamField>

<ParamField body="version" type="string">
  Especifica la versión del webhook enviado. Actualmente 2.
</ParamField>

<ParamField body="retry" type="string">
  Especifica el número de reintentos de esa notificación.
</ParamField>

<ParamField body="data" type="object">
  Especifica el [pago](/reference/payments/the-payment-object) (para el tipo payment) o el [objeto de método de pago](/es/reference/payment-methods-direct-workflow/the-payment-method-object-api) (para inscripciones y otros objetos).

  <Expandable title="propiedades">
    <ParamField body="idempotency_key" type="string">
      Identificador que se usa para omitir entregas duplicadas. Se mantiene estable en todos los reintentos del mismo evento. Su ubicación depende del evento: los eventos de pago ordinarios (incluidos reembolso y contracargo) lo incluyen en `data.payment.idempotency_key`, `payment.split_update` lo incluye en `data.split_update.idempotency_key` y los eventos de suscripción lo incluyen en `data.idempotency_key`. En los eventos `subscription.*` identifica la suscripción y no el evento, por lo que debes eliminar los duplicados de esos eventos usando `type_event` junto con esta clave. Consulta [De-duplication](/docs/webhooks#de-duplication) para ver los detalles de cobertura.
    </ParamField>
  </Expandable>
</ParamField>

<ParamField body="x-hmac-signature" type="string">
  Opcional. La firma HMAC-SHA256 que se envía en el encabezado HTTP para la verificación del webhook cuando la autenticación HMAC está habilitada.
</ParamField>

## Webhooks de actualización de split {#split-update-webhooks}

Estos ejemplos abreviados muestran solo los campos necesarios para interpretar `payment.split_update`; también se incluyen los campos normales del pago. Este evento requiere una suscripción explícita y está pendiente de disponibilidad en el catálogo de producción.

En v2, el sobre identifica `type_event: "payment.split_update"` y el bloque de la operación es `data.split_update`:

```json
{
  "type": "payment",
  "type_event": "payment.split_update",
  "version": 2,
  "retry": 0,
  "data": {
    "split_update": {
      "idempotency_key": "4a518553-a6e7-4717-a415-06084ea85c99",
      "updated_at": "2026-09-22T04:20:00Z"
    },
    "payment": {
      "transactions": {
        "split_marketplace": []
      }
    }
  }
}
```

Este ejemplo borra el split, por lo que el `split_marketplace` de la operación es `[]`. Un reemplazo aplicado incluye en su lugar las entradas de split de esa operación. `transactions` es un único objeto, no un arreglo.

El v1 heredado envía el cuerpo del pago sin el sobre v2 ni `type_event`. Identifica este evento por el bloque `split_update` junto a `payment`:

```json
{
  "split_update": {
    "idempotency_key": "4a518553-a6e7-4717-a415-06084ea85c99",
    "updated_at": "2026-09-22T04:20:00Z"
  },
  "payment": {
    "transactions": {
      "split_marketplace": []
    }
  }
}
```

| Campo | Significado |
| --- | --- |
| `split_update.idempotency_key` | La clave de la solicitud original de actualización de split. Úsala para distinguir operaciones y eliminar entregas duplicadas, dentro del alcance de la cuenta y el tipo de evento. |
| `split_update.updated_at` | La hora de finalización registrada de la operación, que se conserva en la resolución repetida y en la notificación retrasada. |
| `payment.transactions.split_marketplace` | La instantánea del split de la operación seleccionada, incluido `[]` cuando se borra. |

Si `transactions_history` está habilitado, su entrada para la transacción afectada incluye el mismo split de la operación. El evento no habilita el historial ni reemplaza el `payment.split_marketplace` a nivel de pago; no uses ese campo a nivel de pago como la instantánea de esta operación. Los demás campos reflejan la lectura del pago cuando se prepara la notificación y pueden incluir cambios posteriores. Usa `GET /v1/payments/{payment_id}` para obtener el estado más reciente del pago.

No se garantiza que la instantánea de la operación se serialice igual que una lectura posterior del pago. La escala numérica puede variar (por ejemplo, `5` frente a `5.0`) y un objeto de responsabilidad que contenga solo `chargebacks` puede representarse de forma distinta en el mapeo del pago activo. Compara los valores y su significado, en lugar de exigir igualdad byte por byte del JSON. Estas diferencias de representación no identifican una nueva operación de split.

Solo este evento agrega `split_update`; los payloads de compra y de reembolso no incorporan el bloque. Consulta [Split update notifications](/docs/webhooks#split-update-notifications) para conocer el comportamiento de suscripción, emisión, orden y entrega.

## Pago {#payment}

### Webhook de pago V2 {#payment-webhook-v2}

Payload de ejemplo:

<Info>
  Los payloads de webhook de los eventos correspondientes a un método de pago de transferencia bancaria incluyen `payment.payment_method.payment_method_detail.bank_transfer.bank_id`. El campo refleja el `bank_id` enviado en la solicitud de pago original y se omite cuando no se seleccionó ningún banco.
</Info>

<Info>
  Cuando el pago incluye una selección de envío (por ejemplo, elegida dentro de un widget de billetera con [Fast Checkout shipping](/es/docs/payment-features/fast-checkout-shipping)), el payload incluye un nodo `payment.shipping` de nivel superior (con la misma forma que en [el objeto de pago](/reference/payments/the-payment-object)) tanto en la versión V1 como en la V2, y `payment.customer_payer.shipping_address` se completa a partir de él cuando el pagador no tenía ninguna. La clave `shipping` se omite cuando el pago no tiene una selección.
</Info>

<Info>
  Cada transacción incluye `connection_data`, que identifica la conexión del proveedor que la procesó. Usa `connection_data.id` como identificador estable para atribuir las transacciones a una conexión específica cuando operas varias conexiones para el mismo proveedor. `connection_data.name` es el nombre para mostrar configurado en el Dashboard de Yuno y puede ser `null` en algunos eventos, como las transacciones de seguimiento.
</Info>

<Info>
  El campo `transactions` tiene un significado distinto según la superficie. En los payloads de webhook, `data.payment.transactions` es un **único objeto** (la transacción que activó el evento), y `transactions_history` incluye la lista completa de las transacciones del pago cuando está habilitado para el pago (consulta la nota siguiente). En los endpoints de consulta de pagos (`GET /payments/{payment_id}` y `GET /payments?merchant_order_id=`), `transactions` es un **arreglo** que contiene todas las transacciones del pago.
</Info>

<Info>
  `transactions_history` es **opt-in**: solo se completa cuando el pago se creó con `response_additional_data.transactions_history: true` en la solicitud de [Create Payment](/es/reference/payments/create-payment). De lo contrario, los webhooks lo entregan como un arreglo vacío `[]` (el valor predeterminado, que mantiene pequeño el tamaño de los payloads). Esto importa en los pagos que tu enrutamiento reintenta entre proveedores: sin el indicador, el webhook final muestra solo la última transacción, y los intentos anteriores solo se ven mediante `GET /payments/{payment_id}`. Los pagos creados por flujos administrados por Yuno que no establecen el indicador (por ejemplo, las renovaciones de suscripción) también entregan `[]`. Los eventos de contracargo siempre incluyen el historial completo.
</Info>

<Info>
  Nombre de los campos: la geolocalización del cliente se serializa como `geo_location` en los payloads de webhook y como `geolocation` en los endpoints de consulta de pagos. Procesa cada superficie según corresponda.
</Info>

### subscription.creation_failed {#subscriptioncreationfailed}

Se envía para los pagos de [Stripe Billing](/es/docs/payment-features/subscriptions/stripe-billing) cuando un pago `SUCCEEDED` que incluye `external_subscription` no pudo crear su suscripción de Stripe. El dinero está capturado y no se creó ni se activó ninguna suscripción de Stripe. Se envía una vez por cada falla. No se envía cuando el pago ya está reembolsado o reembolsado parcialmente. Suscríbete con el valor `CREATION_FAILED` en `subscription_triggers`.

A diferencia de los demás eventos de suscripción, `data` no incluye un objeto de suscripción de Yuno, porque no existe ninguno:

| Campo | Tipo | Descripción |
| :---- | :--- | :---------- |
| `payment_id` | string (UUID) | El pago de Yuno que fue capturado. |
| `external_subscription` | object | El objeto `external_subscription` exactamente como lo enviaste en el pago. |
| `dead_letter_kind` | string | Por qué no se creó la suscripción, por ejemplo `incomplete_payload`, `tax_quote_expired`, `tax_not_calculated` o `stripe_resource_missing`. Trátalo como un valor abierto: se pueden agregar nuevos valores. |
| `reason` | string | Una descripción breve y legible de `dead_letter_kind`. No la analices programáticamente. |
| `occurred_at` | string (ISO 8601, UTC) | Cuándo Yuno dejó de intentar crear la suscripción. |

### Cobros de renovación y fallas (sin `subscription.error`) {#renewal-charges-and-failures-no-subscriptionerror}

<Warning>
**No existe un webhook `subscription.error`**. Yuno no emite un evento de suscripción cuando falla un cobro de renovación. Los resultados de los cobros de renovación, tanto los recobros exitosos como los intentos fallidos o rechazados, se entregan como webhooks `payment.purchase` vinculados a la suscripción, con el resultado en los campos `status`/`sub_status`. Suscríbete a `payment.purchase` para seguir los resultados de las renovaciones. Los ciclos de `$0`/prueba no emiten ningún webhook de pago; en las suscripciones basadas en planes se informan como [`subscription.cycle_executed`](#subscription-cycle_executed).
</Warning>

<Note>
El **cobro** de la renovación siempre se señala mediante un webhook `payment.purchase`, nunca mediante un webhook de suscripción. El arreglo `payments` dentro del objeto de suscripción está siempre vacío actualmente en los payloads de webhook. `subscription.active` se envía cuando la suscripción se activa por primera vez (en `billing_cycles.current` = 2), no en cada renovación; solo se envía de nuevo cuando una suscripción se recupera de `PAST_DUE`.
</Note>

<Note>
Una renovación fallida sí genera un webhook de suscripción en dos casos. Donde el estado `PAST_DUE` está habilitado para la cuenta, el primer cobro fallido de un ciclo pasa la suscripción a `PAST_DUE` y emite [`subscription.past_due`](#subscription-past_due). Y si la suscripción tiene `retries.cancel_on_exhausted_retries` establecido en `true`, cuando los reintentos de ese ciclo terminan sin un pago exitoso la suscripción se cancela y se emite un único [`subscription.cancel`](#subscription-cancel) con `cancellation_source` establecido en `RETRIES_EXHAUSTED`. Esto sigue sin ser un `subscription.error`: los intentos fallidos individuales siguen siendo webhooks `payment.purchase`. Solo la cancelación final se señala en la suscripción.
</Note>
