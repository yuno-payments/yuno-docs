`createPayment` es el controlador que sobrescribes cuando quieres crear el pago en tu propio backend en lugar de dejar que lo haga el SDK. El SDK entrega el token de un solo uso a tu manejador y espera a que indiques que el pago fue creado.

## Comportamiento {#behavior}

Si no sobrescribes este controlador, el SDK crea el pago automáticamente después de la tokenización, gestiona 3DS si es necesario y entrega el estado final a `onStatus`.

Cuando lo sobrescribes, el SDK entrega el token a tu manejador y espera a que se resuelva la Promise/Task devuelta antes de continuar. En Web, el SDK no establece ningún tiempo de espera para tu manejador. Resuelve la Promise en todos los caminos, incluido un fallo de red, o la transacción se queda en curso. Resuelve la Promise/Task cuando tu backend haya creado el pago llamando a la [API de creación de pago](https://docs.y.uno/reference/payments/create-payment) (`POST /v1/payments`); entonces el SDK consulta el estado del pago, gestiona 3DS si es necesario e invoca `onStatus`.

En Web, envía `token.token` como el token de un solo uso y `token.checkout_session` como la sesión de checkout. Después de un rechazo de tarjeta reintentable, el SDK mueve el formulario a una nueva sesión de checkout, por lo que la sesión de la configuración de tu transacción puede estar desactualizada. Si estableces [`autoContinuePayment: false`](/es/docs/yuno-sdk/reference/objects-you-pass#autocontinuepayment), el SDK se detiene después de que tu manejador se resuelve. No ejecuta ninguna consulta de estado ni 3DS, no llama a `onStatus` y marca la sesión de checkout como finalizada, por lo que un `start()` o `submit()` posterior sobre ella lanza un error. El botón de PayPal ignora el indicador y siempre continúa.

Si la Promise/Task se rechaza, el SDK detiene el flujo. En Web, `onStatus` se dispara entonces con `status: "INTERNAL_ERROR"` y `message.code: "MERCHANT_CREATE_PAYMENT_FAILED"`. `showLoading` emite `isLoading: false` y la vista se cierra en ese momento. Tú eres responsable de mostrar el error a tu usuario. En React Native, el resultado sigue al SDK nativo subyacente: en Android, `onStatus` recibe `INTERNAL_ERROR` con `message.code: "MERCHANT_CREATE_PAYMENT_FAILED"` y tu mensaje de error en `message.reason`; en iOS, el flujo se cierra sin un estado.

En iOS puedes crear el pago tú mismo solo para algunos métodos. Llama a `SdkPayments.defaultCreatePayment(token:)` desde tu sobrescritura para recurrir a la creación de pago propia del SDK, que necesita una sesión creada con `workflow: "SDK_SEAMLESS"`:

```swift
func createPayment(token: [String: Any]) async throws {
    guard createsPaymentsOnBackend else {
        try await SdkPayments.defaultCreatePayment(token: token)
        return
    }
    try await myBackend.createPayment(token: token)
}
```

En React Native, devuelve `SdkPayments.defaultCreatePayment(token)` desde tu sobrescritura. Se resuelve cuando el SDK ha creado el pago, con el mismo requisito de `workflow: "SDK_SEAMLESS"`:

```tsx
createPayment: async (token) => {
  if (!createsPaymentsOnBackend) {
    return SdkPayments.defaultCreatePayment(token);
  }
  await myBackend.createPayment(token);
},
```

En un flujo de inscripción, este controlador no se invoca con datos de pago y sobrescribirlo no tiene efecto. En Web, la configuración de inscripción no acepta `createPayment`. TypeScript lo rechaza y JavaScript lo ignora.

<Warning>
Haz coincidir el `workflow` de la sesión de checkout con esta decisión. Las sesiones creadas con el workflow predeterminado (`SDK_CHECKOUT`) requieren esta sobrescritura, porque el backend rechaza la creación de pagos que proviene del SDK. Si no sobrescribes `createPayment`, crea la sesión con `workflow: "SDK_SEAMLESS"`. El campo está en el [cuerpo de `POST /v1/checkout/sessions`](https://docs.y.uno/reference/checkout-sessions/create-checkout-session#body-workflow), no en `TransactionConfig`.
</Warning>

En un [pago dividido](/es/docs/yuno-sdk/features/split-payment), el token es un token compuesto. Envíalo a `POST /v2/payments` con `workflow: "SDK_CHECKOUT"`, porque `POST /v1/payments` lo rechaza.

## OneTimeToken {#onetimetoken}

`OneTimeToken` es un diccionario/mapa que contiene el valor del token más metadatos asociados.

| Plataforma | Tipo |
|---|---|
| Web | `CreatePaymentTokenInformation`. Los campos de `OneTimeToken` (`token`, `type`, `vaulted_token`, `vault_on_success`, `customer`, `card_data`, `bank_transfer`) más `checkout_session`, y `recognitionToken` y `quote` cuando están presentes. |
| iOS | `[String: Any]` |
| Android | `Map<String, Any>` |
| React Native | `OneTimeToken` (`Record<string, unknown>`), con las claves del token nativo de la plataforma |

Consulta [`OneTimeToken`](/es/docs/yuno-sdk/reference/objects-you-receive#one-time-token) para la referencia completa.

## Hilos de ejecución {#threading}

En iOS y Android, `createPayment` se invoca en el hilo principal. Puedes actualizar la UI directamente desde este manejador. Pero ten en cuenta que cualquier llamada al backend que hagas debe ejecutarse fuera del hilo principal. En React Native se ejecuta en el hilo de JavaScript, y el SDK nativo espera la Promise devuelta.
