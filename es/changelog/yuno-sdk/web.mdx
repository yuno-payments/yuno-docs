## v2.8.1 {#v281}
*November 18, 2026*

**Google Pay**

- <ChangelogBadge type="fixed" /> **Google Pay sigue a updateCheckoutSession**  
  Un botón de Google Pay que ya está montado ahora toma la sesión de checkout establecida por `updateCheckoutSession` (o por un reintento de pago): la hoja muestra el monto y la moneda de la nueva sesión, y el token de un solo uso y el pago usan la nueva sesión. Se ignora un toque mientras la configuración de la nueva sesión todavía se está cargando.

**Apple Pay**

- <ChangelogBadge type="fixed" /> **Apple Pay sigue a updateCheckoutSession**  
  Un botón de Apple Pay que ya está montado ahora toma la sesión de checkout establecida por `updateCheckoutSession` (o por un reintento de pago): la hoja de pago muestra el monto y la moneda de la nueva sesión, y el token de un solo uso y el pago usan la nueva sesión. Se ignora un toque mientras la configuración de la nueva sesión todavía se está cargando. Si esa configuración no se puede cargar, el botón se oculta y vuelve cuando se carga una sesión posterior.

## v2.8.0 {#v280}
*November 18, 2026*

**Formulario del cliente**

- <ChangelogBadge type="added" /> **Los bancos en mantenimiento siguen visibles, pero no se pueden seleccionar**  
  Cuando la lista de emisores marca un banco como fuera de línea, el selector de bancos lo muestra en un grupo "Temporalmente no disponible", con la etiqueta de fuera de línea y sin poder seleccionarse con clic ni con el teclado. Un banco fuera de línea no se puede enviar: el formulario le pide al comprador que elija otro banco. Las listas sin bancos fuera de línea se dibujan exactamente como antes.

**Lite Web SDK**

- <ChangelogBadge type="added" /> **Ventana emergente de inscripción e inscripción de tarjeta, KakaoPay y PAYCO de KCP**  
  Cuando el proveedor de una inscripción responde con una acción de ventana emergente, la inscripción ahora abre la página del proveedor en una ventana propia del SDK en lugar de reemplazar la página. La página del comercio permanece montada detrás de una superposición de inscripción, y el SDK resuelve el estado de la inscripción como antes, así que no hace falta cambiar la integración. Si el navegador bloquea la ventana, el comprador recibe un botón Continuar. Las inscripciones respondidas con una redirección simple mantienen la redirección en la misma pestaña. Una ventana de tarjeta de KCP abierta en esa ventana emergente ya no falla con un error de integración de tarjeta (신용카드 연동 오류) y se completa en la ventana emergente. La inscripción también sigue una acción REDIRECT_URL que pide un POST de formulario a un host de KCP (https, *.kcp.co.kr): el SDK envía un formulario oculto a init_url una vez por inscripción. Cualquier otra redirección mantiene el GET. En navegadores de escritorio, la inscripción de KakaoPay (`KAKAO_PAY`) y PAYCO (`KCP_PAYCO`) a través de KCP muestra un botón que abre la ventana de KCP al hacer clic y reenvía el resultado de KCP a la URL de resultado de la inscripción (solo un host de Yuno o el host apiUrl de marca blanca), de modo que el comprador llega a la página de éxito o de error del comercio. Si KCP no carga, se bloquea el envío del resultado o el comprador cierra KCP sin un resultado, el botón se habilita de nuevo con un error en línea para que el comprador pueda reintentar. Al desmontar el SDK se cierra la ventana de KCP. Los comercios con una Content Security Policy estricta necesitan los hosts de KCP en script-src y frame-src, y form-action para el host de la URL de resultado (*.y.uno, o el host apiUrl de marca blanca) y *.kcp.co.kr.

**Apple Pay**

- <ChangelogBadge type="fixed" /> **Apple Pay se muestra cuando el comprador no tiene tarjeta en la billetera**  
  El botón de Apple Pay ya no se oculta cuando el comprador no tiene tarjeta en Apple Wallet: se muestra siempre que el dispositivo es compatible con Apple Pay, y la hoja de Apple permite al comprador agregar una tarjeta durante la compra. Esto se aplica en todos los lugares donde el SDK lo dibuja (la lista de métodos de pago y la vista de la billetera de Apple Pay de `getPaymentMethodsViews`), y `transaction.isPaymentMethodAvailable({ paymentMethodType: 'APPLE_PAY' })` ahora devuelve `true` para esos compradores. El SDK ya no llama a `ApplePaySession.applePayCapabilities()`, lo que también elimina una solicitud a los servidores de Apple antes de que se muestre el botón.

**SDK principal**

- <ChangelogBadge type="fixed" /> **Sin error del formulario de tarjeta después de que la página elimina el elemento del SDK**  
  Cuando la página del comercio eliminaba el elemento que le dio al SDK sin llamar a `transaction.unmount()` (por ejemplo, cuando el comprador presionaba atrás mientras el checkout se estaba cargando), el SDK informaba `Element card-form-<uuid> doesn't exist in the DOM` como un estado de error a través de `onStatus`. Ese estado de error ya no se entrega en este caso. La lista de métodos de pago que se estaba dibujando en el elemento eliminado queda como estaba hasta que el pago se resuelve, el SDK se inicializa de nuevo o la lista se vuelve a montar, como antes.

**Checkout**

- <ChangelogBadge type="changed" /> **La lista de métodos de pago muestra sus métodos antes**  
  La lista de métodos de pago muestra sus métodos de pago antes de que el SDK descargue los formularios de pago. Los formularios se descargan justo después, en segundo plano, y un formulario abierto antes de que llegue su código muestra el marcador de carga que el formulario ya usa mientras se inicia.

## v2.7.2 {#v272}
*November 12, 2026*

**Pagos con tarjeta**

- <ChangelogBadge type="fixed" /> **Una tarjeta guardada ya no paga sola cuando fallan las cuotas**  
  Cuando la consulta de cuotas de una tarjeta de crédito guardada fallaba y las cuotas eran su único campo obligatorio, el SDK creaba el token de un solo uso y el pago sin ningún clic en pagar. En la lista de métodos de pago, la tarjeta guardada preferida se selecciona mientras carga el checkout, por lo que pagaba en cuanto el SDK se montaba, por ejemplo cuando el monto no tiene plan de cuotas (`NO_INSTALLMENT_PLAN_AVAILABLE`). Ahora una consulta fallida significa que no hay cuotas: la tarjeta guardada se muestra con su botón de pago y no se paga nada hasta que el comprador haga clic en pagar o elija otro método de pago.

**SDK principal**

- <ChangelogBadge type="changed" /> **Registro de la presencia del contenedor al montar**  
  Cuando el elemento que se pasa al SDK no está en la página al momento de montar, o salió de la página y se dibujó de nuevo, el SDK ahora registra si el elemento estaba ahí cuando comenzó y cuántos milisegundos después salió. Sin cambios para el comprador.

**Checkout**

- <ChangelogBadge type="changed" /> **Lista de métodos de pago y botones de billetera más rápidos**  
  La lista de métodos de pago y los botones de billetera cargan más rápido: el SDK descarga su código mientras carga la configuración del checkout en lugar de después, y los botones de billetera reutilizan los métodos de pago que el SDK ya solicitó, por lo que hacen una solicitud menos. Los botones express sobre la lista mantienen su lugar mientras cargan, de modo que los métodos de pago de abajo no se mueven cuando aparece un botón.

## v2.7.1 {#v271}
*November 11, 2026*

**Checkout**

- <ChangelogBadge type="fixed" /> **El CVV de la tarjeta guardada y el PIN de la tarjeta usan la fuente del comercio**  
  Los campos del código de seguridad y del PIN de la tarjeta en el formulario de tarjeta guardada ahora cargan las fuentes pasadas en `card.fonts`, igual que el formulario de tarjeta nueva, por lo que ya no vuelven a la fuente predeterminada del navegador.

- <ChangelogBadge type="added" /> **Pagos rápidos de Mercado Pago en start() headless**  
  Un `start()` headless con `MERCADO_PAGO_SUPERTOKEN` ahora envía los campos de billetera de Mercado Pago (`thirdPartyToken`, `providerMethodId`, `providerMethodType`) y las cuotas en el token de un solo uso. Si falta algún campo de billetera, `onStatus` informa `WALLET_DATA_MISSING` y no se crea ningún token.

## v2.7.0 {#v270}
*November 10, 2026*

**PayPal**

- <ChangelogBadge type="added" /> **Botón solo de Venmo**  
  Cuando Disable Funding Sources incluye paypal y Enable Funding Sources incluye venmo, el checkout muestra solo el botón de Venmo. PayPal permanece junto a Venmo cuando paypal no está deshabilitado. Con paypal deshabilitado y venmo no habilitado, no se muestra ningún botón.

**Checkout**

- <ChangelogBadge type="changed" /> **Sesión de comercio de Apple Pay e inscripción de PayPal bajo demanda**  
  Cuando la configuración marca la sesión de comercio de Apple Pay o la inscripción de PayPal como bajo demanda, el SDK la solicita al endpoint sdk-provider cuando el comprador toca el botón en lugar de leerla de la configuración, por lo que no se crea ningún token de configuración de PayPal para compradores que nunca hacen clic en PayPal. El botón de PayPal permanece visible sin un token de configuración en la configuración. Si la solicitud falla, la hoja de Apple Pay o la ventana de PayPal se cierra y el comprador puede tocar de nuevo mientras el resto del checkout sigue funcionando.

## v2.6.0 {#v260}
*November 6, 2026*

**Pagos con tarjeta**

- <ChangelogBadge type="added" /> **Divide un pago entre dos tarjetas**  
  `transaction.start([...])` recibe un arreglo de dos métodos de pago con tarjeta, cada uno con su `data.amount`. El SDK crea un token compuesto, se lo entrega a `createPayment`, ejecuta el 3DS de cada tarjeta por turno y envía un solo `onStatus` para todo el pago. Con `autoContinuePayment: false` se detiene después de `createPayment` y tú continúas cada tarjeta de tu lado. Un arreglo no válido rechaza `start()` con `INVALID_SPLIT_PAYMENT` antes de cualquier solicitud.

## v2.5.1 {#v251}
*November 5, 2026*

**Checkout**

- <ChangelogBadge type="fixed" /> **La inscripción en Click to Pay vuelve a funcionar cuando el comprador marca la casilla de consentimiento**  
  En el formulario de tarjeta de Golden Flow, al marcar "Save my information with Mastercard Click to Pay" se veía la marca, pero el SDK la recibía como desmarcada, por lo que la tarjeta se pagaba como una tarjeta normal y nunca se inscribía en Click to Pay. "Remember me in this browser" y la casilla de consentimiento del mandato tenían el mismo problema. Las tres ahora informan lo que ve el comprador.

- <ChangelogBadge type="changed" /> **Cada billetera express que activas ahora se muestra como botón**  
  Con el apilado horizontal de botones express, cada billetera cuyo interruptor Render as express button esté activado ahora se muestra como botón express, en el orden de tu lista. Dos reglas sacaban billeteras de la fila: Google Pay pasaba a la lista de métodos de pago en cuanto se activaba una segunda billetera express, y la fila se detenía en tres botones. Ambas se eliminaron. En lugar de quitar una billetera para que las demás quepan, la fila se ajusta: los botones mantienen un ancho igual, una fila contiene dos en un teléfono y tres cuando hay espacio, y una última línea corta se centra. El orden de la lista, el respaldo a la lista cuando un botón no carga y el apilado vertical se comportan como antes. Los comercios con dos o más billeteras express activadas verán a Google Pay pasar de la lista a la fila, y los comercios con más de tres verán cada billetera como botón en dos o más líneas.

## v2.5.0 {#v250}
*November 3, 2026*

**Checkout**

- <ChangelogBadge type="added" /> **Los campos del cliente que ya enviaste pueden estar ocultos, de solo lectura o editables**  
  Cuando la sesión de checkout incluye un cliente y el Checkout Builder define un estado para un campo del cliente, el formulario lo sigue: un campo oculto no se muestra y su valor se sigue enviando con el pago, un campo de solo lectura muestra el valor bloqueado con un icono de candado y un campo editable muestra el valor prellenado para que el comprador pueda cambiarlo solo para este pago. El SDK verifica cada valor oculto y de solo lectura con la misma validación que el formulario: un valor que no la pasa se muestra editable con su error. Cuando todos los campos están ocultos y son válidos, se omite el formulario. Si no se pueden cargar los datos de país que necesita la verificación de documento, teléfono o dirección, esos valores se envían tal cual. Sin un estado, sin un cliente o sin un valor, los campos se comportan como antes.

- <ChangelogBadge type="changed" /> **La lista de métodos de pago se muestra antes que los botones de billetera**  
  La lista de métodos de pago ahora aparece en cuanto se renderizan sus métodos de pago, sin esperar los botones de Google Pay o Apple Pay. Una billetera que carga lento o nunca carga ya no mantiene la lista detrás de un indicador de carga hasta por 5 segundos.

**Apple Pay**

- <ChangelogBadge type="changed" /> **Apple Pay carga antes en la lista de métodos de pago**  
  En la lista de métodos de pago, el SDK ahora empieza a cargar el botón de Apple Pay y el SDK de Apple en cuanto llegan los métodos de pago, cuando Apple Pay está en la lista, por lo que los botones de billetera aparecen antes. Nada cambia cuando Apple Pay no se ofrece o no se puede mostrar en el dispositivo.

**SDK principal**

- <ChangelogBadge type="changed" /> **Los registros de rendimiento incluyen el tiempo desde el inicio del SDK**  
  Los registros de rendimiento ahora incluyen el tiempo transcurrido desde que el comercio llamó a `start()`, de modo que los inicios lentos se pueden rastrear desde la primera llamada del comercio.

- <ChangelogBadge type="changed" /> **Los tiempos de descarga de los chunks del SDK se informan como métricas de red**  
  Los chunks JS y CSS de carga diferida del propio SDK ahora informan su tiempo de descarga como métricas de red, con los aciertos de caché marcados, por lo que las cargas lentas de chunks aparecen en el monitoreo. El comportamiento de carga y los tiempos no cambian.

- <ChangelogBadge type="changed" /> **Un registro de rendimiento marca cuándo se renderizaron todos los botones externos**  
  En la lista de métodos de pago, el SDK registra una vez cuando todos los botones externos terminaron de cargar, como lo hace el Web SDK 1.11.

- <ChangelogBadge type="changed" /> **Las cargas de chunks y billeteras sin terminar se registran cuando la página se oculta**  
  Cuando la página se oculta mientras la descarga de un chunk o un botón de billetera sigue cargando, el SDK registra qué cargas seguían abiertas y por cuánto tiempo.

Los compradores sin tarjeta en Wallet (`paymentCredentialsUnavailable`) siguen sin verlo.

## v2.3.0 {#v230}
*October 29, 2026*

**Inscripción**

- <ChangelogBadge type="added" /> **Token guardado en el resultado de onStatus de la inscripción**  
  Cuando una inscripción termina con el estado ENROLLED, el resultado entregado a `onStatus` ahora incluye `vaultedToken` con el token del método de pago guardado, en todas las rutas de inscripción. Los otros estados y los resultados de pago no incluyen el campo.

**Checkout**

- <ChangelogBadge type="fixed" /> **Las cuentas de PayPal guardadas ya no muestran el banner "Unauthorized payment"**  
  Al seleccionar una cuenta de PayPal guardada cuya consulta de cuotas no devuelve planes, ya no se muestra el banner "Unauthorized payment. There are no payment options available" de NuPay. Ese banner es una regla propia de NuPay y solo aplica a NuPay; una cuenta de PayPal guardada sin planes paga como cualquier otro método de pago guardado.

**SDK principal**

- <ChangelogBadge type="fixed" /> **Las vistas de billetera siguen showStatusScreen**  
  Las vistas de billetera de `getPaymentMethodsViews` (Apple Pay, Google Pay, PayPal, Samsung Pay, Revolut Pay y PayPal Braintree) ignoraban el `showStatusScreen` de la transacción y siempre mostraban la pantalla de estado del SDK, por lo que con `showStatusScreen: false` `onStatus` esperaba a que el comprador hiciera clic en Continue. Ahora siguen el valor de la transacción, como lo hace la lista de métodos de pago: con `false` no se muestra ninguna pantalla de estado y `onStatus` se dispara sin ella.

- <ChangelogBadge type="fixed" /> **El montaje espera un contenedor tardío**  
  Cuando el elemento indicado en elementSelector todavía no está en la página, el SDK ahora espera hasta 3 segundos a que aparezca antes de informar ELEMENT_NOT_FOUND. Nada cambia cuando el elemento ya está ahí.

## v2.2.0 {#v220}
*October 27, 2026*

**SDK principal**

- <ChangelogBadge type="added" /> **Los métodos de pago con redirección pueden abrirse en una ventana emergente**  
  Cuando una conexión con un proveedor está configurada para abrir su redirección en una ventana emergente, los métodos de pago basados en redirección abren al proveedor en una ventana propiedad del SDK en lugar de reemplazar la página. La página del comercio permanece montada, y el SDK espera el resultado del pago, cierra la ventana y dispara los callbacks de resultado existentes, por lo que no se necesita ningún cambio en la integración. La ventana se abre en el paso en el que antes se redirigía la página; cuando el navegador la bloquea, el comprador recibe un botón Continue to payment. Las conexiones sin esa configuración mantienen la redirección en la misma pestaña.

- <ChangelogBadge type="fixed" /> **Una segunda transacción en la misma página llama a createPayment**  
  Cuando una página ejecutaba un pago sin `createPayment` y luego un pago con `createPayment` usando el formulario del SDK, el segundo creaba el pago por sí mismo e informaba `INVALID_CHECKOUT_SESSION`. Ahora entrega el token a `createPayment`, como lo hace cuando es la primera transacción de la página.

**Fraude y riesgo**

- <ChangelogBadge type="added" /> **Sesión de dispositivo de Risk.js de Checkout.com**  
  Cuando una conexión enrutada a Checkout.com tiene `RISK_JS_ENABLED` activado, una `PUBLIC_KEY` y el subdominio específico del comercio (`MSSD`), el SDK carga Risk.js de Checkout.com en segundo plano cuando se monta el método de pago, publica los datos del dispositivo y envía el `deviceSessionId` devuelto con el token y el pago como el id de sesión de terceros `CHECKOUT`, para que Checkout.com pueda reenviarlo como `risk.device_session_id`. Aplica a todos los métodos de pago enrutados a Checkout.com (tarjetas, billeteras y métodos de pago alternativos). Una falla en la carga del script, la inicialización o la publicación nunca bloquea el checkout: la entrada se deja vacía, la falla se registra y la siguiente solicitud publica de nuevo. Checkout.com conserva la sesión de dispositivo durante 20 minutos después de emitirla, por lo que un checkout que permanece abierto más tiempo paga sin ella.

**Checkout**

- <ChangelogBadge type="changed" /> **Los campos de tarjeta siguen el color de campo del Checkout Builder**  
  Cuando el color de campo del Checkout Builder es un color distinto de blanco, los campos de número de tarjeta, fecha de vencimiento y CVV y las sugerencias de dirección lo adoptan. Su texto usa los colores de texto del Checkout Builder y los bordes y las opciones resaltadas se mezclan a partir de los colores de texto y de campo, de modo que el texto claro sobre un campo oscuro sigue siendo legible. Nada cambia cuando el color de campo es blanco o no está definido, y los estilos pasados en `card.styles` se siguen aplicando encima (sdk-web-card 1.93.0).

- <ChangelogBadge type="fixed" /> **Espaciado y divisor de More options**  
  En los diseños Moon Active y plegado, la sección "More options" tiene espacio encima y muestra el divisor "Or pay with" entre los botones express y los demás métodos de pago.

## v2.1.2 {#v212}
*October 20, 2026*

**Transacción**

- <ChangelogBadge type="added" /> **Verifica si un método de pago se mostrará antes de listarlo**  
  El nuevo [`transaction.isPaymentMethodAvailable({ paymentMethodType })`](/es/docs/yuno-sdk/reference/objects-you-receive#checking-payment-method-availability-web) devuelve `true` o `false` para cualquier tipo de método de pago, con la misma decisión que toma el SDK antes de mostrar ese método en la sesión de checkout. Los comercios que dibujan su propia lista de métodos de pago pueden llamarlo y ocultar los métodos que no se mostrarían.

**Checkout**

- <ChangelogBadge type="fixed" /> **Los nombres de los métodos de pago mantienen la fuente del checkout**  
  En páginas anfitrionas que definen fuentes en todos los elementos con una regla `*`, el nombre del método de pago y su descripción del Checkout Builder en la lista de opciones usan la fuente, el peso y el espaciado del checkout.

- <ChangelogBadge type="fixed" /> **Los textos de las casillas mantienen la fuente del checkout**  
  En páginas anfitrionas que definen fuentes en todos los elementos con una regla `*`, el texto de cada casilla (guardar tarjeta, guardar al tener éxito, facturación igual a envío, consentimiento del mandato, registro en Click to Pay y remember me) y de las opciones de Click to Pay usa la fuente, el peso y el espaciado del checkout, como los nombres de los métodos de pago (sdk-web-core 9.4.1).

## v2.1.1 {#v211}
*October 19, 2026*

**Pagos con tarjeta**

- <ChangelogBadge type="fixed" /> **La longitud del CVC de la tarjeta sigue al servicio de tarjetas**  
  El campo CVC ahora aplica el `security_code_length` que devuelve el servicio de tarjetas para la marca de la tarjeta, tanto para una tarjeta nueva como para una guardada. Un CVC de 4 dígitos escrito en una marca de 3 dígitos (Elo, Alelo, Edenred, Sodexo, VR) muestra "Invalid security code" en lugar de enviarse, algo que Adyen rechazaba con el código 103 "CVC is not the right length". Amex mantiene 4 dígitos, y las marcas sin longitud del servicio de tarjetas mantienen la regla anterior de 3 o 4. También incluye sdk-web-card 1.91.1: un frame de tarjeta servido desde y.uno ignora un `apiUrl` o `assetUrl` fuera del dominio de Yuno (sdk-web-card 1.92.0).

## v2.1.0 {#v210}
*October 17, 2026*

**Universal Web SDK**

- <ChangelogBadge type="added" /> **Idioma checo en el checkout**  
  Agrega la localización en checo (cs, cs-CZ) al checkout del Universal Web SDK, con los mismos textos que la versión Web SDK 1.11.

- <ChangelogBadge type="added" /> **Descripción del método de pago desde el Checkout Builder**  
  En la lista de métodos de pago, la descripción que el comercio define para un método de pago en el Checkout Builder (`custom_description`) se muestra como una segunda línea gris debajo de su nombre. El texto se muestra completo, se ajusta a tantas líneas como necesite y conserva sus saltos de línea. Los métodos sin descripción, y las tarjetas o cuentas guardadas, se renderizan como antes. Mismo comportamiento que la versión Web SDK 1.11.

- <ChangelogBadge type="fixed" /> **Loader corregido después de la configuración de 3DS**  
  Cuando un pago termina en el paso de configuración de 3DS y el comercio maneja el estado del pago (`showStatusScreen: false`), el SDK ahora oculta su loader en cuanto entrega el resultado. Antes, el loader permanecía en pantalla alrededor de un minuto y luego mostraba un error "Transaction failed", aunque el resultado ya había llegado al comercio. Esto afectaba las autenticaciones solo con 3DS y los pagos con tarjeta rechazados durante la autenticación 3DS. Mismo comportamiento que la versión Web SDK 1.11.

- <ChangelogBadge type="fixed" /> **El fingerprint de EBANX ya no lanza "invalid country"**  
  Cuando la toma de fingerprint de dispositivo de EBANX está configurada y el `countryCode` pasado al SDK es un país que EBANX no admite (por ejemplo `US`), el SDK ya no muestra un error `invalid country` no capturado en cada carga. Ahora el error se captura y se registra, y el fingerprint de EBANX se omite para esa carga. Los pagos no se veían afectados antes ni después de este cambio.
