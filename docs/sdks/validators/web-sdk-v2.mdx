Drop this file in the root of your project and ask your coding agent:

> Validate my Yuno Web SDK v2 integration following this file

It works as `CLAUDE.md`, `AGENTS.md` or a pasted prompt. It only reads code and changes nothing unless you ask.

This validator covers the sdk-web v2 line ("Yuno SDK 2.x"): the global `window.SdkPayments`,
`SdkPayments.initialize(...)` and then `sdk.transaction({...})`. The live release is 2.2.0 (released
2026-10-27), served per full version at `https://sdk-web.y.uno/v2.2.0/main.js`. GA was 2.0.0. The
public docs for it are the "SDK" tab at docs.y.uno (`docs/yuno-sdk/*`), not the legacy "SDKs" tab, which is
1.x.

## How to use

First confirm the repository is on v2. Search source, HTML templates, server templates and `package.json`:

```
grep -rn "SdkPayments\|sdk-payments-ready\|window\.Yuno\|yuno-sdk-ready\|YunoSDK\|sdk-web\.[a-z.]*y\.uno\|sdk-static-bundles-ms/sdk-web\|loadScript(\|@yuno-payments/sdk-web\|\.transaction(\|startCheckout\|startSeamlessCheckout\|mountCheckout" --exclude-dir=node_modules .
```

- **v2:** a script URL matching `/v2.<minor>.<patch>/main.js`, calls to `sdk.transaction(...)`,
  `transaction.start(...)`, `getPaymentMethodsViews(...)`.
- **v1 (1.x):** `/v1.11/main.js` or another 1.x folder, `window.Yuno`, `Yuno.initialize`, `startCheckout`,
  `startSeamlessCheckout`, `mountCheckoutLite`, `mountSeamlessCheckout`, `yunoCreatePayment`,
  `yunoPaymentResult`. Stop and use the v1 validator or the migration validator instead.
- The global name alone does not decide it. Since 1.9.1 the v1 bundle also sets `window.SdkPayments` and
  fires `sdk-payments-ready`. The instance API decides: v2 has `typeof sdk.transaction === 'function'`, v1
  has `startCheckout` and no `transaction`.

Report each check as PASS / FAIL / N/A with the evidence (file:line). Do not pass a check because the code
"looks right": quote the line that proves it. Severity: **(B)** blocking, the payment fails or the result is
wrong; **(W)** warning, degraded or fragile behaviour; **(I)** information.

## The flow being validated

```
<script src="https://sdk-web.y.uno/v2.<m>.<p>/main.js">   sets window.SdkPayments, fires 'sdk-payments-ready' once
await SdkPayments.initialize(publicApiKey, applicationSession?, options?)   // once per page, stable arguments
  -> sdk.transaction(config)               // sync; validates config; throws on invalid config
       -> transaction.start({ paymentMethod: { type, vaultedToken?, data? } })   // form, or headless with data
       -> transaction.getPaymentMethodsViews({ types, onPaymentSelected }) -> views.<x>.mount({ elementSelector })
       -> transaction.submit()             // only for a form that start() mounted, with showPayButton:false
       -> await transaction.secureFields(options?) -> .create({ name, options }).mount(selector)
       -> await transaction.unmount()
  -> sdk.transactionStatus({ checkoutSession, elementSelector, ... })
  -> sdk.antifraud({ checkoutSession, countryCode, ... })
  -> onStatus({ status, substatus, message })   // client signal only; confirm by webhook or GET payment
```

Mode: `createPayment` present with a `checkoutSession` is manual (the merchant creates the payment). No
`createPayment` is managed (the SDK creates it, the session needs `workflow: "SDK_SEAMLESS"`). Enrollment
(`customerSession`) is always managed. There is no `window.Yuno`, no `yuno-sdk-ready`, no `on()`, no `close()`.

## Checks

### Loading and bootstrap

**1. The script is v2 and pinned to a full version (V1, B)**
- Grep `sdk-web\.(y\.uno|sandbox\.y\.uno|staging\.y\.uno|prod\.eu\.y\.uno)/[^"' ]*main\.js`,
  `sdk-static-bundles-ms/sdk-web/`, `loadScript(` and `@yuno-payments/sdk-web`.
- PASS: the URL matches `/v2\.\d+\.\d+/main.js`, or the SRI URL `.../sdk-web/v2.<m>.<p>/main.js`.
- FAIL on `/v1.11/`, `/v2/`, `/v2.2/`, `latest`; on `loadScript()` without `baseUrl` (it loads `/v1.11/`); on
  `loadScript({ sri: true })` (hard-coded v1.11.40 SRI URL). For npm, `baseUrl: 'https://sdk-web.y.uno/v2.x.y'`.
- Why: a v1 bundle gives `sdk.transaction is not a function`; rolling folders `/v2/`, `/v2.0/`, `/v2.2/`
  return 404. There is no rolling v2 folder: bumps are manual. The EU host `sdk-web.prod.eu.y.uno` served
  only up to 2.1.2 on 2026-10-29 (verify at runtime for the pinned version).

**2. No v1 globals or events (V2, B)**
- Grep `window\.Yuno|\bYuno\.initialize|new Yuno|yuno-sdk-ready|YunoSDK`. FAIL on any hit in v2 code.
- Why: v2 sets only `window.SdkPayments`: `Yuno is not defined`, or `yuno-sdk-ready` never fires.

**3. Ready handling covers "script already loaded" (V3, B)**
- Grep `sdk-payments-ready` and `SdkPayments`. PASS: `if (window.SdkPayments) start(); else
  window.addEventListener('sdk-payments-ready', start)`, or an awaited `loadScript` / own load promise.
- FAIL on a bare `addEventListener` (the event fires once, at bundle load), or `SdkPayments.initialize`
  called where the script tag is not guaranteed to have run.
- Why: checkout never starts on pages where the script loaded first; `SdkPayments is not defined`.

**4. `initialize` is awaited, client-side, with the public key only (V4, B)**
- Grep `SdkPayments\.initialize\(`; check `await` or `.then`; check it is not in server code
  (`getServerSideProps`, server components, route handlers); check no private secret key in front-end code.
- FAIL if the result is used without `await`, if it runs on the server, or if a private key is bundled.
- Why: `initialize` returns `Promise<SdkPayments>`: `sdk.transaction is not a function` or `Cannot read
  properties of undefined`; on the server, `window is not defined`.

**5. `initialize` arguments are stable and one instance is reused (V5, W)**
- Look for `initialize` in render functions, in effects without a module-level cache, or with an argument
  that changes per call (`applicationSession` per checkout, `Date.now()`, random values).
- FAIL on more than one distinct argument set per page lifetime, or one `initialize` per transaction.
- Why: same arguments return the same instance and log `SdkPayments.initialize() was called again with the
  same arguments. The existing instance was returned; the SDK was not re-initialized.` (benign). Different
  arguments tear the old instance down, the mounted form disappears and calls on it throw `This SdkPayments
  instance is no longer active: a later initialize() replaced it. Use the instance returned by the most
  recent initialize().`

### Transaction config and result

**6. The transaction config is valid (V6, B)**
- For each `.transaction(` call. PASS: exactly one of `checkoutSession` / `customerSession`; `countryCode`;
  `onStatus` is a function; `createPayment`, if present, is a function. TypeScript repos must also pass
  `language` and `showStatusScreen` (required by the type although the docs call them optional).
- Why, verbatim throws: `` Provide either `checkoutSession` or `customerSession`, not both. ``,
  `` A `checkoutSession` or `customerSession` is required. ``, `` `countryCode` is required. ``,
  `` `createPayment` must be a function when provided. `` Without `onStatus` the console warns
  `` SdkPayments transaction() was created without an `onStatus` function. The payment result will not be
  delivered to your integration. Pass `onStatus` in the transaction config to receive the result. ``
- Unknown or v1-only keys pass through with no error and are never read. Flag any key not in the v2 type.

**7. `onStatus` handles the full status contract (V7, B)**
- Read the handler. PASS: reads `result.status`, `result.substatus`, `result.message`; handles
  `INTERNAL_ERROR` (branch on `message.code`) and `USER_CANCEL`; treats `INTERNAL_ERROR/FORM_INVALID`,
  `INTERNAL_ERROR/COLLECT_FAILED` and, in manual mode, a retryable `DECLINED`/`ERROR` as non-final.
- FAIL on v1 values (`'FAIL'`, `'REJECT'`, `'PROCESSING'`, `'READY'`), two positional arguments, a redirect
  or teardown on every call, or the order marked paid client-side on `SUCCEEDED`.
- Why: branches never match, a first decline ends the retry loop, or orders are fulfilled without payment.
  With `showStatusScreen: true` (default) `onStatus` fires when the shopper dismisses the SDK result screen.

**8. Mode matches the checkout-session `workflow` (V8, B)**
- Front end: is `createPayment` present? Backend: grep `checkout/sessions` and `workflow`.
- PASS: `createPayment` with a default-workflow session; no `createPayment` with `workflow: "SDK_SEAMLESS"`.
- Why: a mismatch ends in `onStatus` `INTERNAL_ERROR`; the backend rejects the SDK's payment creation.

**9. `createPayment` follows the one-argument Promise contract (V9, B)**
- Grep `createPayment\s*[:=(]`. PASS: one parameter `token`; sends `token.token` and `token.checkout_session`
  to the merchant backend; returns a Promise that settles on every path; rejects on backend failure.
- FAIL on `(ott, info, cs)`; the argument used as the token string; the config `checkoutSession` used instead
  of `token.checkout_session`; `catch {}` that resolves; a path that never settles; a `continuePayment()` call.
- Why: an object sent as the token gives a Create Payment 4xx; the session rotates after a retryable decline,
  so the config one is stale; no timeout exists, so a hung promise leaves the form loading forever. A
  rejection ends in `INTERNAL_ERROR` / `MERCHANT_CREATE_PAYMENT_FAILED` with the form still mounted.
- Verify at runtime: a config with only the v1 name `yunoCreatePayment` may run managed, not manual.

**10. `autoContinuePayment: false` is deliberate (V10, W)**
- Grep `autoContinuePayment`. PASS: absent, or `false` with status owned by webhook and a new session for any
  later `start()`.
- Why: with `false` the SDK runs no status query, no 3DS and no `onStatus` after `createPayment` resolves, and
  reusing the session throws the "already finished" error (check 18). PayPal buttons ignore `false`.

### Mounting and paying

**11. `elementSelector` resolves at call time (V11, B)**
- Check `elementSelector` in the config and in each `.mount({ elementSelector })`. The node must exist and be
  connected when `start()` / `mount()` runs. A string selector or an `HTMLElement` are both valid.
- FAIL on a node not yet rendered, conditionally rendered or detached; no selector for a form payment.
- Why, verbatim: `elementSelector "<sel>" was not found in the document.`, `elementSelector is detached from
  the document.`, `Wrong element selector`, `Element <sel> doesn't exist in the DOM` with `onStatus`
  `INTERNAL_ERROR/ELEMENT_NOT_FOUND`.

**12. `start()` is awaited with error handling and is not payment completion (V12, B)**
- Grep `\.start\(`. PASS: inside try/catch or `.catch`; `paymentMethod.type` always set; result read only in
  `onStatus`. A form `start()` resolves when the form is on the page, not when paid.
- FAIL on no catch; `.start()` without `paymentMethod` on a payment; "success" UI after `await start()`; a
  second `start()` on the same mounted form instead of `submit()`.
- Why, verbatim rejections: `` `paymentMethod.type` is required for a payment transaction. ``,
  `` `start()` has already been called on this transaction. Call `submit()` to submit the form it mounted. ``,
  `A payment is in progress on this transaction. Wait for it to settle before starting another payment
  method.` A "paid" screen before the shopper pays is the merchant-visible symptom.

**13. The merchant's own Pay button is wired correctly (V13, W)**
- Check `showPayButton` and the click handler. Form: `showPayButton:false`, `await start({ paymentMethod })`,
  then `transaction.submit()`. List: the button calls `start({ paymentMethod: selected })` with the stored
  `onPaymentSelected` value; `selectionSource === 'auto'` (SDK preselection) does not enable it.
- FAIL on `submit()` before `start()` resolved, or on a list, wallet or enrollment; Pay enabled on `auto`; the
  button not disabled while a payment runs.
- Why, verbatim: `` `submit()` needs a form mounted by `start({ paymentMethod })`. Call `start()` first and wait
  for it to resolve. ``, `` `submit()` does not pay from the payment method list. Call `start({ paymentMethod })`
  with the selected method. ``, `` `submit()` cannot pay a wallet. The shopper pays by tapping the wallet
  button. `` An invalid form delivers non-final `INTERNAL_ERROR/FORM_INVALID`.

**14. Views are requested and mounted correctly (V14, W)**
- Grep `getPaymentMethodsViews` and `\.mount\(`. PASS: `types` only from `paymentMethodList`, `applePay`,
  `googlePay`, `samsungPay`, `paypal`, `paypalBraintree`, `revolutPay`; each view guarded (`?.` or a check);
  each `mount` awaited or `.catch`-ed (typed `void`, returns a Promise); wallets pay on tap, no `start()`.
- FAIL on v1 names (`GOOGLE_PAY`), unguarded `views.x.mount`, no catch, views on an enrollment transaction.
- Why: `Cannot read properties of undefined (reading 'mount')`; unhandled rejection `There are not valid
  payment methods`; thrown `` `getPaymentMethodsViews` is not available for enrollment transactions. Use
  `secureFields()` to collect card data. `` Wallet views stay mounted after `transaction.unmount()`; there is no
  per-view unmount. Verify at runtime: a list plus wallets from one transaction.

**15. Headless data is the v2 envelope and is not logged (V15, B)**
- Grep `data:\s*\{\s*card`. PASS: `data.card.{holderName, number, securityCode, expirationMonth,
  expirationYear}` in camelCase; one `start()` per transaction; card data never logged or stored. A saved card
  with a fresh CVV is `vaultedToken` plus `data.card.securityCode`.
- FAIL on snake_case (`holder_name`, `security_code`, `payment_method.card.detail`), a second headless
  `start()` (single-shot), or `data` while an inline list form is mounted.
- Why: tokenization fails or fields arrive empty; `` `start()` has already been called on this transaction. ``

**16. Secure Fields use the v2 surface (V16, B)**
- Grep `secureFields(`, `\.create\(`, `\.render\(`, `\.mount\(`, `generateToken`, `isFieldComplete`.
- PASS: `const fields = await transaction.secureFields({ installmentEnable? })`;
  `fields.create({ name, options }).mount('#sel')`; Pay gated on `!error && isDirty` per field; payment by
  `transaction.start({ paymentMethod: { type: 'CARD', data: { card: { holderName } } } })`.
- FAIL on `.render(` (v1), `generateToken*` or `continuePayment`, `isFieldComplete` as the gate, PCI keys in
  `data.card`.
- Why: `render is not a function`; the throw `` Secure fields collect the card data inside the mounted iframes —
  remove <keys> from `paymentMethod.data.card`. Only non-PCI metadata (holderName, type, installment,
  customer, vaultOnSuccess) may be passed here. ``; a Pay button that stays disabled for valid shorter PANs.

**17. The enrollment flow is correct (V17, B)**
- Grep `customerSession`. PASS: no `checkoutSession`, `createPayment`, `showPayButton` or
  `autoContinuePayment` with it; `start()` with no arguments for the UI, `start({ paymentMethod: { type, data
  } })` for headless; success is `ENROLLED` (UI) or `CREATED` (headless and Secure Fields).
- FAIL on reading `result.vaultedToken` (never delivered; fetch it server-side), `submit()` or views.
- Why: an `undefined` vaulted token is saved; thrown `` `submit()` is not available for enrollment
  transactions. `` or `` `paymentMethod.type` is required for a headless enrollment. ``

### Re-render and framework lifecycle

**18. One instance, one transaction per mount, cleanup on teardown, StrictMode-safe (V18, B)**

No v2 doc covers React, StrictMode or other frameworks. These rules come from the code constraints: same
`initialize` arguments return the same instance (different ones supersede it); a second `start()` of a
mounted form throws on purpose (a React effect that ran twice once submitted a prefilled form and created a
payment); a new `Transaction` resets shared per-instance state, so two live transactions on one instance
fight and the last mount wins; `transaction.unmount()` is async, delivers `USER_CANCEL` for an unfinished
attempt and leaves wallet views; a settled session cannot be reused.

- **All frameworks:** `initialize` behind a module-level promise (or always the same arguments); one
  `transaction()` per mounted checkout, created where the container already exists; one live card surface
  per page; a new checkout session means a new transaction. FAIL on `initialize` or `transaction()` in a
  render body, or two transactions mounted at once.
- **React:** the transaction is held in a `useRef` and created in the `useEffect` that owns the container;
  `start()` runs once per transaction (guard with the ref); cleanup calls `await transaction.unmount()` and
  clears the ref; callbacks (`onStatus`, `createPayment`) read the latest props through a ref so a re-render
  does not rebuild the transaction. Under StrictMode the effect runs, cleans up and runs again: PASS only if
  the second run builds a fresh transaction after the cleanup, never a second `start()` on the first one.
  FAIL on `start()` in an effect without cleanup, or effect dependencies that change every render.
- **Next.js:** SDK code runs only in the browser: a `'use client'` component calling `initialize` inside an
  effect, or a component loaded with `dynamic(..., { ssr: false })`. FAIL on `SdkPayments` in a server
  component, `getServerSideProps`, a route handler, or module top level of a server-rendered file.
- **Vue (guidance):** create the transaction in `onMounted` (or `mounted`) and `await transaction.unmount()`
  in `onBeforeUnmount`; keep it out of reactive state (`shallowRef` or a plain variable).
- **Angular (guidance):** create it in `ngAfterViewInit` (the container exists) and unmount in `ngOnDestroy`;
  run SDK calls outside zone change detection loops if they re-trigger renders.
- **SPA teardown:** leaving the checkout route calls `await transaction.unmount()`; the `USER_CANCEL` it
  delivers is not shown as an error or treated as abandonment; wallet containers are removed with the route.
- Why: duplicated or vanishing forms, double payment attempts, `` `start()` has already been called on this
  transaction. ``, `The payment on this checkout session already finished. Create a new checkout session and
  transaction to pay again.`, or an error banner on every route change.
- Verify at runtime: `transaction.unmount()` reads the shared root after its awaits; a StrictMode remount
  picking the wrong root is not tested anywhere. Report StrictMode findings as "unverified against a real
  remount".

### Options and edges

**19. `showLoading` is a function and the merchant owns the loader (V19, W)**
- Grep `showLoading` and `onLoading`. PASS: `showLoading: (isLoading) => void` that shows and hides the
  merchant's loader; a registered handler replaces the SDK overlay.
- FAIL on `showLoading: true|false` or `onLoading` (v1 name, not read), or a handler with no UI behind it.
- Why: blank screen with no loader while tokenizing. Verify at runtime: a boolean is expected to throw
  `showLoading is not a function` (inferred from code, not run).

**20. The status screen option uses the v2 name (V20, W)**
- Grep `showPaymentStatus|showStatusScreen|transactionStatus`. PASS: `showStatusScreen`; `transactionStatus`
  receives `elementSelector` (required). FAIL on `showPaymentStatus` (ignored, the result screen still shows).
- Why: duplicated result UI, and `onStatus` delayed until the shopper dismisses the SDK screen.

**21. Card options use v2 names (V21, W)**
- Grep `card:\s*\{`. PASS: `saveCardEnabled`, `styles`, `type`, `vaultOnSuccess`, `texts`, `documentEnable`,
  `isCreditCardProcessingOnly`, `fonts`. FAIL on `cardSaveEnable` or `requiredFieldsOrderedEnabled`.
- Why: `cardSaveEnable` is silently ignored and the save-card checkbox disappears. Verify at runtime:
  `externalButtons.applePay.topLevelDomain` left the public type; whether it still works is unknown.

**22. Antifraud reads the result union (V22, W)**
- Grep `\.antifraud\(`. PASS: checks `result.status === 'success'` before using `result.deviceFingerprints`.
  FAIL on reading `deviceFingerprints` without the check, or relying on a rejection.
- Why: `undefined` fingerprints reach the backend and fraud screening runs without them. It never rejects.

**23. CSS overrides, white-label, CSP and host assumptions (V23, W)**
- Always run this part, even when the repo has no white-label or CSP setup: grep every stylesheet and
  component style (`*.css`, `*.scss`, `*.less`, styled blocks in `*.ts`, `*.tsx`, `*.vue`, `*.svelte`) for
  `yuno-` and `Yuno-`. Any selector on those names is a v1 name that v2 does not render; the v2 names are
  `sdk-payments-*`.
- Then check `apiUrl`, `assetUrl`, CSP headers and proxy rules, when present.
- PASS: overrides target `sdk-payments-*`; a proxy forwards `/sdk-static-bundles-ms/*`; `apiUrl` and
  `assetUrl` set together; the v2 host is in CSP `script-src`; on a page that must contain no `yuno` string,
  an `HTMLElement` selector has its own `id`.
- FAIL on `.yuno-*` selectors, a missing CSP host, or an id-less element on a white-label page.
- Why: overrides stop applying, the script is blocked, or the SDK assigns `yuno-view-<random>` as the id.
  Verify at runtime: only three class names were compared with v1, so check each override visually.

### Server side

**24. Fulfilment is confirmed on the server, and TypeScript types are v2 (V24, B)**
- Find the payment webhook handler or the `GET /v1/payments/...` check that drives fulfilment. TypeScript:
  look for a local declaration of `window.SdkPayments`.
- PASS: fulfilment from webhook or `GET payment`; a local `.d.ts` copied from the v2 API report.
- FAIL on fulfilment from `onStatus`; `@yuno-payments/sdk-web-types` used for v2 calls (v1 shape, no
  `transaction`). The typing part alone is (W).
- Why: orders marked paid without a payment, or compile errors and silent `any` around the SDK.

## Report format

```
CHECK  1  Script v2, full version     PASS  public/index.html:14 https://sdk-web.y.uno/v2.2.0/main.js
CHECK  8  Mode vs workflow            FAIL  api/session.ts:31 no workflow, front end has no createPayment
                                            (managed on SDK_CHECKOUT -> INTERNAL_ERROR)
CHECK 17  Enrollment                  N/A   no customerSession in this repository
SDK: v2.2.0 (script tag). Framework: Next.js 14, React StrictMode on.
```

Finish with the failures ordered by impact, (B) then (W) then (I), each with a one-line fix.

## Diagnostics to capture

1. The script URL and version actually served, and `typeof sdk.transaction` in the console.
2. The checkout session id, its `workflow`, the country and the UTC time of the attempt.
3. Every `onStatus` payload received (`status`, `substatus`, `message.code`, `message.reason`).
4. Console warnings and errors from the SDK, quoted verbatim (initialize, superseded, onStatus missing).
5. The merchant's Create Payment request and response (card data removed), the framework and StrictMode state,
   and whether the failure follows a route change or a re-render.
