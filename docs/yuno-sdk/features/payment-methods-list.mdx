`getPaymentMethodsViews` returns pre-built views for the payment methods you want to show. Use it to display the SDK's full payment methods list, a wallet button (Apple Pay or Google Pay), or any combination available on your platform.

This feature applies to payment flows only. It is not available for enrollment.

<Note>
**The list is selection-only.** It renders payment methods for the shopper to choose from, but does not process payments on its own. After the shopper picks a method, you call `Transaction.start()` to process the payment. This makes the list composable with any payment flow — including headless integrations where you collect the payment data yourself. Mount the list for method selection, receive the selection through `onPaymentSelected`, and pass it to `start()` with your own pre-collected `data`. See [Headless mode](/docs/yuno-sdk/migration/web/headless) for the full headless integration.
</Note>

## This is what the list looks like

The SDK renders the full list of payment methods enabled in your dashboard: logos, names, and the shopper's saved methods included. And if you prefer fewer taps, you can choose to show each method's form expanded right inside the list, so shoppers enter their details without leaving it, for a faster checkout. You enable the expanded layout from the **Checkout Builder** in your [Yuno Dashboard](https://dashboard.y.uno/), no code needed.

## Unfolded configuration

The **unfolded** (expanded) layout shows each payment method's form directly inside the list row, so the shopper can enter their details immediately after selecting a method — no navigation, no extra tap. Enable it from **Checkout Builder → Styling → Unfolded display** in your [Yuno Dashboard](https://dashboard.y.uno/).

When unfolded is enabled:
- The form renders inline as soon as the shopper selects a method.
- `start({ paymentMethod })` submits the already-filled form — it acts as your Pay action.
- Express wallets (Apple Pay, Google Pay, PayPal) still render their native buttons inside the row.

When unfolded is disabled (the default):
- The list shows method names and logos only.
- `start({ paymentMethod })` mounts the selected method's form into your `elementSelector` and resolves.
- The shopper pays from that form's button, or from your own button if you set `showPayButton: false` and call `transaction.submit()`.

<Tip>
**Combine selection-only with headless.** Even with unfolded disabled, you can use the list purely for selection and skip the SDK's forms entirely. Receive the selection through `onPaymentSelected`, then call `start({ paymentMethod: { ...selection, data: yourCollectedData } })` to process the payment with data you collected yourself. The SDK tokenizes your data and handles 3DS.
</Tip>

## Before you start

Your backend must have created a `checkoutSession` and the `Transaction` must be constructed with that session. See [Get Started](/docs/yuno-sdk/get-started).

## Implementation

Call `getPaymentMethodsViews` with the types you want and a controller. The SDK returns a map of `PaymentMethodType` to view. Embed each view in your layout. When the user picks a method, your controller receives a `PaymentMethodSelected` that you pass to `Transaction.start()`.

<Tabs>
  <Tab title="Web">

```typescript
let selectedPaymentMethod: PaymentMethodSelected | null = null

const views = transaction.getPaymentMethodsViews({
    types: ['applePay', 'googlePay', 'paymentMethodList'],
    onPaymentSelected: (paymentMethod) => {
        selectedPaymentMethod = paymentMethod
    },
})

views.applePay?.mount({ elementSelector: '#apple-pay', buttonType: 'buy', buttonStyle: 'black' })
views.googlePay?.mount({ elementSelector: '#google-pay', buttonColor: 'black' })
views.paymentMethodList?.mount({ elementSelector: '#payment-list' })

// Later, when the user confirms (e.g. your Pay button):
if (selectedPaymentMethod) {
    transaction.start({ paymentMethod: selectedPaymentMethod })
}
```

Each view in the returned object exposes a `.mount({ elementSelector, ...config })` method. Per-view styling (Apple Pay button type, Google Pay color, etc.) lives on `.mount()`. Options you pass to a wallet's `mount()` override the same keys in the transaction config's `externalButtons`. `paymentMethodList.mount()` also takes `scrollContainerSelector`, `visibleTriggerOffsetPx`, and `bottomOffsetPx` for a list inside a scrolling container. They override the same keys in the transaction config's `paymentListConfig`.

What `start()` does after a selection depends on the Checkout Builder. With forms unfolded inside the list, `start({ paymentMethod })` submits the form the shopper already filled in, so it is your Pay action. With folded forms, `start()` mounts the selected method's form into the `elementSelector` of your transaction config and resolves. The shopper then pays from that form's button. If you set `showPayButton: false`, call `transaction.submit()` from your own button instead. Pass `elementSelector` on the transaction config so the folded form has somewhere to render.

  </Tab>

  <Tab title="iOS">

```swift
var selectedPayment: SdkPayments.PaymentMethodSelected?

let views = transaction.getPaymentMethodsViews(
    types: [.APPLE_PAY(), .PAYMENT_METHOD_LIST],
    controller: self
)

// In your SdkPayments.PaymentListController:
func onPaymentSelected(paymentSelected: SdkPayments.PaymentMethodSelected) {
    selectedPayment = paymentSelected
}

// Later, when the user confirms (e.g. your Pay button):
if let selectedPayment {
    transaction.start(paymentSelected: selectedPayment)
}
```

The views are SwiftUI `AnyView`s. For a UIKit layout, call `getPaymentMethodsViewsUIKit(types:controller:)` instead: same arguments, and it returns `[PaymentMethodType: UIView]`, ready to add as subviews.

  </Tab>

  <Tab title="Android">

```kotlin
var selectedPayment: PaymentMethodSelected? = null

val views = transaction.getPaymentMethodsViews(
    host = this,
    types = listOf(PaymentMethodType.GooglePay(), PaymentMethodType.PaymentMethodList),
    controller = this
)

// In your PaymentListController:
override fun onPaymentSelected(paymentSelected: PaymentMethodSelected) {
    selectedPayment = paymentSelected
}

// Later, when the user confirms (e.g. your Pay button):
selectedPayment?.let { transaction.start(activity = this, paymentSelected = it) }
```

  </Tab>
</Tabs>

## PaymentMethodType

| Value | Available on | What you get |
|---|---|---|
| `APPLE_PAY` | iOS, Web | The native Apple Pay button, wired to start the payment flow. On iOS this is an enum case with associated values — write it as `.APPLE_PAY()`, or pass `type:` / `style:` to customize the button. |
| `GOOGLE_PAY` | Android, Web | The native Google Pay button, wired to start the payment flow. |
| `PAYPAL` | Web | The native PayPal button, wired to start the payment flow. |
| `PAYPAL_BRAINTREE` | Web | The PayPal button for accounts that process PayPal through Braintree. |
| `SAMSUNG_PAY` | Web | The Samsung Pay button, wired to start the payment flow. |
| `REVOLUT_PAY` | Web | The Revolut Pay button, wired to start the payment flow. |
| `PAYMENT_METHOD_LIST` | iOS, Android, Web | Full list of payment methods enabled in your Yuno dashboard. |

On Web, pass the values as camelCase strings in `types`: `'applePay'`, `'googlePay'`, `'paypal'`, `'paypalBraintree'`, `'samsungPay'`, `'revolutPay'`, and `'paymentMethodList'`.

On Android, a type that does not apply to the platform or configuration comes back as `null`. On iOS every requested type comes back with a view. On Web every requested type is returned and the check happens in `mount()`. When the wallet is not enabled for the checkout session, the SDK logs `There are not valid payment methods`, reports the failure through `onStatus`, and the promise that `mount()` returns rejects. `mount()` is typed `void`, so `await` it to catch that rejection, and mount only the wallets enabled for the session.

<Note>
On Android, `PaymentMethodType` is a sealed interface rather than a set of string constants: `GOOGLE_PAY` corresponds to `PaymentMethodType.GooglePay(...)`, which also carries the button customization (`cta`, `theme`, `cornerRadius`), and `PAYMENT_METHOD_LIST` corresponds to `PaymentMethodType.PaymentMethodList`. `APPLE_PAY` does not exist on Android.

On iOS, `APPLE_PAY` is an enum case with associated values, both optional: `.APPLE_PAY(type: .buy, style: .black)` takes a `PKPaymentButtonType` and a `PKPaymentButtonStyle` (defaults `.plain` and `.automatic`), which carry the Apple Pay button customization. The bare spelling `.APPLE_PAY` does not compile — always write `.APPLE_PAY()`.
</Note>

### Express buttons

`APPLE_PAY`, `GOOGLE_PAY`, and `PAYPAL` return the native express buttons, ready to use. You style them through the standard view modifiers of each platform (size, padding, corner radius, etc.). The SDK only adds a loader on top while the payment flow is initializing. On Web, `PAYPAL_BRAINTREE`, `SAMSUNG_PAY`, and `REVOLUT_PAY` are express buttons too, and you style all of them through the options of `mount()`.

<Note>
You do not need to call `Transaction.start()` for express buttons. Tapping the button is the user's confirmation, so the SDK starts the transaction internally and reports the result through `onStatus`.

This also holds inside the list on Web. When the shopper selects an express wallet row, its button renders inside the row and is the pay control. `start()` for that selection returns without doing anything, so hide your own Pay button while `onPaymentSelected` reports an express type (`APPLE_PAY`, `GOOGLE_PAY`, `PAYPAL`, `PAYPAL_BRAINTREE`, `SAMSUNG_PAY`, or `REVOLUT_PAY`).
</Note>

## PaymentListController

The controller you pass to `getPaymentMethodsViews`. On iOS and Android only `onPaymentSelected` is required. On Web `onPaymentSelected` is optional, but without it the list cannot tell you what the shopper picked, so pass it whenever you request `'paymentMethodList'`.

| Method | Required | Platforms | Behavior |
|---|---|---|---|
| `onPaymentSelected(paymentSelected)` | Yes (Web: optional) | iOS, Android, Web | Invoked when the user picks a payment method. Pass the `PaymentMethodSelected` to `Transaction.start()`. |
| `onHeightChange(newHeight)` | No\* | iOS, Android | Invoked when the rendered view's height changes, so you can apply it to your layout. |
| `onUnenroll(success)` | No | iOS, Android | Invoked after the SDK has attempted to remove a saved payment method initiated from the list. Receives a boolean indicating whether the unenroll succeeded. |

<Note>
**\* `onHeightChange` is optional to _implement_, but you must apply the reported height when your layout constrains the list.**
</Note>

On Web and iOS, `onPaymentSelected` can fire before any tap. When the list preselects the shopper's preferred method on mount, the callback runs with `selectionSource: 'auto'` (`.auto` on iOS). A tap runs it with `selectionSource: 'user'` (`.user` on iOS). On Web it also fires when the shopper taps an express button you mounted. The Web `PaymentMethodSelected` is `{ type, name?, vaultedToken?, selectionSource? }`. Keep the latest value and pass it to `start()` only from your own Pay control.

<Note>
If the list cannot be loaded because the payment methods service fails, the SDK reports it through your `TransactionController.onStatus` with status `INTERNAL_ERROR` and a `message`: `source` `backend` with the backend error code in `code` (the HTTP status when the body has none) and the error body in `raw`, or `source` `sdk` for network failures, with `context` `MethodsViewImplementation.getPaymentMethods` on iOS and `paymentMethodList.getPaymentMethods` on Web. The list stays empty: show your own error state or request the views again to retry.
</Note>

<Note>
The **Edit / remove** control that lets a shopper delete a saved method — and the only thing that makes `onUnenroll` fire — is rendered only when **`edit_payment_method_list`** is enabled in **Checkout Builder → Styling** in your [Yuno Dashboard](https://dashboard.y.uno/). It is **off by default** on iOS and Android, so until you turn it on the saved methods show no remove affordance and `onUnenroll` is never invoked. The same setting controls the remove control on Web. Web has no `onUnenroll` callback. After a removal the SDK refetches the session's payment methods and the list re-renders.
</Note>

## Notes

- `getPaymentMethodsViews` is synchronous.
- You can request any combination of types available on your platform in a single call.
- The `PaymentMethodSelected` delivered by `onPaymentSelected` is what you pass to `Transaction.start()`. See [Get Started](/docs/yuno-sdk/get-started).
- **Checking method availability before mounting custom lists (Web):** If you build your own custom payment method selector instead of using `paymentMethodList`, use [`transaction.isPaymentMethodAvailable({ paymentMethodType })`](/docs/yuno-sdk/reference/objects-you-receive#checking-payment-method-availability-web) to verify whether express wallets (such as `APPLE_PAY` or `GOOGLE_PAY`) or specific methods are eligible to render on the customer's current device and checkout session before displaying them.
- On Web, once a payment on the session reaches a final status, the SDK removes the list and marks the checkout session as finished. `start()`, `submit()`, and `mount()` on that session then throw. To pay again, create a new checkout session and a new `Transaction`, or call `transaction.updateCheckoutSession()` with the new session, then mount the list again.
