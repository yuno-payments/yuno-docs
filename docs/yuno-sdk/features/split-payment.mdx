A split payment lets the shopper fund one order with two cards. Each card pays its own part of the total, you create one payment, and you receive one result.

You pass an array to `start()` instead of a single payment method. The SDK creates one composite token, hands it to [`createPayment`](/docs/yuno-sdk/controllers/create-payment), runs the 3DS of each card and reports the outcome in [`onStatus`](/docs/yuno-sdk/controllers/on-status).

In this phase, split payment applies to cards only. To divide a payment among marketplace recipients, see [Split payments marketplace](/docs/payment-features/split-payments-marketplace) instead.

## Before you start

- **Ask Yuno to enable it.** Split payment is enabled per account. Without it, the token request fails with `SPLIT_NOT_ENABLED`.
- **Create the checkout session with the full amount.** Use the total of the order and the default `SDK_CHECKOUT` workflow.
- **Override `createPayment`.** You create the payment from your backend. See [Create the payment](#create-the-payment).
- **Collect the card data in your own UI.** Pass it in the object. The flow does not mount an SDK form or a payment methods list for the cards.
- **Pass each amount with the decimals of its currency.** The SDK sends the value as you give it. See [Amount precision](#amount-precision).

## Build the object

Each item of the array is the same object you pass for one payment method in `start()`, plus the `amount` that card pays.

### Rules for the items

- **Number of items:** two, one per card.
- **Order:** the first item is charged and authenticated first, then the second.
- **`amount`:** required on every item, with `currency` and `value`.
- **Card data:** every item carries a card or a vaulted token. The backend rejects an item with neither or with both.
- **Same card twice:** not allowed. The SDK compares the card numbers and the vaulted tokens.
- **Currency:** the same on every item, and the currency of the checkout session. The SDK checks the items against each other and the backend checks them against the session.
- **Sum of the amounts:** must equal the amount of the checkout session. The backend validates it.
- **Payment method type:** only cards in this phase. The backend validates it.
- **Other card fields:** each item accepts the installment plan and the save-card option of a one-card [`TransactionData`](/docs/yuno-sdk/reference/objects-you-pass#transaction-data). They apply to that card only.

### Amount precision

The SDK sends `value` exactly as you pass it. It does not round. The backend rejects a value with more decimals than the currency has with `AMOUNT_PRECISION`, so pass each amount with the decimals of its currency, for example two for `BRL`.

Floating-point arithmetic can add decimals you did not write. `259.9 - 100` is `159.89999999999998` on every platform, and the SDK sends it like that. Compute the parts in minor units as integers and convert at the end, or round each `value` to the decimals of the currency before you build the object.

## Complete example

Build the object, start the payment, create it in `createPayment` and receive the result in `onStatus`. This example splits a checkout session of 300 BRL into 200 BRL on a new card and 100 BRL on a vaulted card.

<Tabs>
  <Tab title="Web">

```typescript
const sdkPayments = await SdkPayments.initialize('<PUBLIC_API_KEY>')

const transaction = sdkPayments.transaction({
  checkoutSession: '<CHECKOUT_SESSION>',
  countryCode: 'BR',
  createPayment: async (token) => {
    // Your backend calls POST /v2/payments with the composite token
    await myBackend.createSplitPayment({
      token: token.token,
      checkout_session: token.checkout_session,
    })
  },
  onStatus: (result) => {
    // One result for the whole payment
    console.log(result.status, result.substatus)
  },
})

try {
  await transaction.start([
    {
      paymentMethod: {
        type: 'CARD',
        data: {
          amount: { currency: 'BRL', value: 200 },
          card: {
            number: '4111111111111111',
            securityCode: '123',
            expirationMonth: 11,
            expirationYear: 29,
            holderName: 'VIVI AMEZQUITA',
          },
        },
      },
    },
    {
      paymentMethod: {
        type: 'CARD',
        vaultedToken: 'aad8578e-ac2f-40a0-8065-25b5957f6555',
        data: {
          amount: { currency: 'BRL', value: 100 },
        },
      },
    },
  ])
} catch (error) {
  // An invalid array rejects start() before any request
  if (error.code === 'INVALID_SPLIT_PAYMENT') {
    console.error(error.message)
  }
}
```

## Create the payment

The token you receive in `createPayment` is one composite token for both cards. It carries `token`, `checkout_session` and `expires_at`, and no card data. Read it from the `token` key. From your backend, send it to `POST /v2/payments` with `workflow: "SDK_CHECKOUT"`, and return from `createPayment` when the request is done. The SDK then continues with the 3DS of each card.

<Warning>
`POST /v1/payments` rejects a composite token. Use `POST /v2/payments`.
</Warning>

```bash
curl --request POST \
  --url https://api-sandbox.y.uno/v2/payments \
  --header 'X-Idempotency-Key: <UUID>' \
  --header 'public-api-key: <PUBLIC_API_KEY>' \
  --header 'private-secret-key: <PRIVATE_SECRET_KEY>' \
  --header 'content-type: application/json' \
  --data '{
    "account_id": "<ACCOUNT_ID>",
    "merchant_order_id": "order-10047",
    "description": "Order paid with two cards",
    "country": "BR",
    "amount": { "currency": "BRL", "value": 300 },
    "workflow": "SDK_CHECKOUT",
    "checkout": { "session": "<CHECKOUT_SESSION>" },
    "customer_payer": { "id": "<CUSTOMER_ID>" },
    "payment_method": { "token": "<COMPOSITE_TOKEN>" }
  }'
```

| Field | Description |
|---|---|
| `amount` | The total of the payment: the sum of the card amounts. |
| `workflow` | `SDK_CHECKOUT`. |
| `checkout.session` | The checkout session you passed to the transaction. |
| `customer_payer` | The payer, shared by both cards. |
| `payment_method.token` | The composite token. Do not send the cards again: the token carries them. |

See [Create Payment (two cards)](/reference/payments/create-payment-v2) for the full request, and [Pay with two cards](/docs/payment-features/pay-with-two-cards) for the response and the operations on each card.

## Receive the result

You receive the result in `onStatus`, at payment level. There is no callback per card.

The SDK runs card 1 and then card 2. If card 1 fails, card 2 does not start and `onStatus` reports the status of the payment. If the shopper closes the challenge of card 1, card 2 does not start either: `onStatus` receives `USER_CANCEL` on iOS and Android, and `PENDING` with `substatus` `USER_CANCEL` on Web, as for any 3DS challenge.

If card 2 fails after card 1 was authorized, what happens to card 1 is handled on the backend. The payment response on your server shows the final state of each card: see [Pay with two cards](/docs/payment-features/pay-with-two-cards).

On iOS, `onStatus` can report a non-final `PENDING` first, as for any payment. See [`onStatus`](/docs/yuno-sdk/controllers/on-status), and confirm the outcome on your server before you fulfill the order.

## Errors

### SDK validations

The SDK checks the shape of the array before it requests the token, so an invalid array sends no request. The code is `INVALID_SPLIT_PAYMENT`, the message is in English and cards are numbered from 1. The message is for your developers: do not show it to the shopper.

| Platform | How you receive it |
|---|---|
| Web | `start()` rejects with an error that carries `code` and `message`. `onStatus` is not called. |
| iOS, Android | `onStatus` receives `status: "INTERNAL_ERROR"`, with `INVALID_SPLIT_PAYMENT` in `message.code` and the text in `message.reason`. |

The three SDKs run the same checks, in this order, and stop at the first one that fails:

| Check | iOS and Android message | Web message |
|---|---|---|
| One item | `paymentsSelected needs at least 2 items, got 1` | `payment_method needs at least 2 items, got 1` |
| An item without `amount` | `paymentsSelected[2].transactionData.amount is required` | `payment_method[2].amount is required` |
| `amount.value` not greater than 0 | `paymentsSelected[2].transactionData.amount.value must be greater than 0` | `payment_method[2].amount.value must be greater than 0` |
| An item without `amount.currency` | `paymentsSelected[2].transactionData.amount.currency is required` | `payment_method[2].amount.currency is required` |
| A currency different from the first item | `paymentsSelected[2].transactionData.amount.currency must match paymentsSelected[1]` | `payment_method[2].amount.currency must match payment_method[1]` |
| The same card or vaulted token twice | `paymentsSelected[2] uses the same card as paymentsSelected[1]` | `payment_method[2] uses the same card as payment_method[1]` |

Everything else, such as the payment method type, an item with neither a card nor a vaulted token, the sum of the amounts and the currency of the session, is validated by the backend with the codes in [Backend errors](#backend-errors).

### Backend errors

The backend validates the composite token request. When it rejects the request, `onStatus` receives `status: "INTERNAL_ERROR"` with `message.source` `backend` and no token reaches `createPayment`.

On Web, `start()` also rejects with the same error. On Web and iOS, `message.code` is the backend code below. On Android, `message.code` is the HTTP status and the backend code is inside `message.raw`.

| Code | Meaning |
|---|---|
| `SPLIT_NOT_ENABLED` | Split payment is not enabled for the account. Ask Yuno to enable it. |
| `METHOD_COUNT_OUT_OF_RANGE` | The number of items is outside what the account allows. |
| `METHOD_TYPE_NOT_ALLOWED` | The payment method type is not allowed for split payment. |
| `AMOUNT_SUM_MISMATCH` | The sum of the amounts differs from the checkout session amount. |
| `CURRENCY_MISMATCH` | A currency differs from the checkout session currency. |
| `AMOUNT_NOT_POSITIVE` | An amount is not greater than 0. |
| `AMOUNT_PRECISION` | An amount has more decimals than the currency allows. See [Amount precision](#amount-precision). |
| `DUPLICATE_INSTRUMENT` | The same card or vaulted token appears in two items. |
| `CARD_TOKEN_INVALID` | An item has neither a card nor a vaulted token, has both, or uses a vaulted token that does not belong to the customer. |
| `INSTALLMENT_PLAN_UNAVAILABLE` | The installment plan of an item is not available. |
| `INSTALLMENT_PLAN_LOOKUP_FAILED` | Yuno could not look up the installment plan. |
| `SEQUENCE_INVALID`, `TOTAL_MISMATCH`, `CAPTURE_MODE_MISMATCH`, `INVALID_REQUEST` | The request does not meet the token contract. Check the backend message in `message.reason` or `message.raw`. |
