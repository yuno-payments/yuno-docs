A webhook is how Yuno tells your system about events, like a payment authorized, a subscription renewed, or a payout completed, without you having to poll for them. You configure a destination `url`, the events you want (triggers), and how Yuno authenticates to your endpoint. Yuno then delivers each event as an HTTP `POST` as soon as it happens.

To receive webhooks, your endpoint must be a public HTTPS URL that accepts an unauthenticated `POST` request. This is safe because the URL you configure is only ever called by Yuno, and you can verify every delivery is genuine with one of the [authentication methods](/reference/webhooks#delivery-authentication) below.

## Delivery and retries

Yuno expects an **HTTP 200 OK** response to confirm a notification was received. No response body is required. If it doesn't get one in time, Yuno retries up to seven times on the schedule below, so a brief outage on your end doesn't lose an event.

| Attempt | Deadline after the first try |
| :------ | :---------------------------- |
| First try | N/A |
| Second try | 5 minutes |
| Third try | 50 minutes |
| Fourth try | 6 hours |
| Fifth try | 24 hours |
| Sixth try | 48 hours |
| Seventh try | 96 hours |

## De-duplication

Because Yuno retries delivery when it doesn't receive a confirmation, your endpoint can receive the same event more than once. This is expected behavior, not a bug: your integration should be able to identify and skip duplicates.

### The identifier

For ordinary v2 payment events, the key is `data.payment.idempotency_key`; for subscription events, it is `data.idempotency_key`. It stays stable across every retry of the same event, so you can use it to tell a duplicate delivery apart from a genuinely new event.

For `payment.split_update`, use `data.split_update.idempotency_key` instead: it identifies the split update operation. The payment's existing `data.payment.idempotency_key` can be shared by several different split updates. Scope your de-duplication record by account, event type, and operation key. In legacy v1 payloads, use the top-level `split_update.idempotency_key`.

### Coverage

The key location depends on the event:

- Ordinary payment events, including refund and chargeback: `data.payment.idempotency_key`
- Split update events: `data.split_update.idempotency_key`
- Subscription events: `data.idempotency_key`

<Warning>
For `subscription.*` events the key identifies the **subscription**, not the event: it is the `X-Idempotency-Key` sent when the subscription was created, and it is repeated identically on every lifecycle event for that subscription. De-duplicate `subscription.*` events on `type_event` **plus** `data.idempotency_key` — matching on the key alone collapses every event for a subscription into one and silently drops `subscription.active`, `subscription.cancel` and the rest.
</Warning>

<Note>
Support for `enrollment` events is planned but not yet available. Until then, enrollment payloads do not include `data.idempotency_key`.
</Note>

### Why you might see the same event twice

Each v2 payload also includes a top-level `retry` field with the number of delivery attempts made for that event (`0` on the first attempt). If your endpoint doesn't return an HTTP 200 OK in time, Yuno resends the same event (same event-specific idempotency key, incremented `retry`) following the schedule described in [Delivery and retries](#delivery-and-retries) above. Treat any event whose `type_event` and idempotency key you've already processed as a duplicate, regardless of its `retry` value.

### Recommended handling

For v2 payloads, store the event-specific key you've successfully processed together with the account and event's `type_event`, and check incoming events against that store before acting on them:

```js
async function handleWebhookEvent(event) {
  // Scope the key by event type: a subscription's key is the same on every
  // one of its lifecycle events.
  const operationKey = event.type_event === "payment.split_update"
    ? event.data.split_update.idempotency_key
    : event.type_event.startsWith("payment.")
      ? event.data.payment?.idempotency_key
      : event.data.idempotency_key;
  if (!operationKey) {
    throw new Error("Missing event key: use an event-specific fallback");
  }
  const key = `${event.account_id}:${event.type_event}:${operationKey}`;

  if (await store.has(key)) {
    // Already processed, acknowledge and skip.
    return;
  }

  await processEvent(event);
  await store.add(key);
}
```

Keep in mind that not every event type carries an idempotency key yet (see Coverage above). For event types without it, fall back to your own de-duplication key, such as the combination of resource ID and event type.

## Split update notifications

<Note>
`payment.split_update` requires the split-update trigger to be available in your account's webhook catalog. Production subscription availability is pending; this event is not enabled by a purchase or refund subscription.
</Note>

Subscribe explicitly to `SPLIT_UPDATE` in `payment_triggers` when the catalog makes it available. Existing `PURCHASE` and `REFUND` subscriptions and their payloads do not change.

A notification is initiated after the split update is recorded as applied. It is also initiated after a manual resolution commits `APPLY_REQUESTED` (apply the requested split) or `SET_EMPTY` (clear the split). `KEEP_PREVIOUS`, failed or unresolved updates, same-key request replays, and repeated resolutions do not initiate another notification.

The payload includes `split_update.idempotency_key`, the original split update request key, and `split_update.updated_at`, the recorded completion timestamp of that operation. This timestamp is not the webhook send time or the payment's general update time. See the [v1 and v2 examples](/docs/webhooks/object-and-examples#split-update-webhooks).

The event's `payment.transactions.split_marketplace` is the split recorded for that operation. It remains that operation's split even if a later update completes before delivery. Other payment fields are read when the notification is prepared, so the body is **not a complete historical payment snapshot**. For the latest state, retrieve the payment with `GET /v1/payments/{payment_id}`. Do not overwrite a newer split with an older event; use the operation timestamp when reconciling, and retrieve the payment when the order is ambiguous.

Delivery is not exactly once and events may arrive out of order. The split update can succeed even if notification dispatch fails. Once a notification is accepted for webhook delivery, normal webhook retries can produce duplicate deliveries. De-duplicate by the split operation key, acknowledge receipt, and retrieve the payment when you need its current state.
