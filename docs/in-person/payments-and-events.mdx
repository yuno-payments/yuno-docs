In-store sales use the same `payment` resource as online, with the same `status` and `sub_status`. What is new is the `channel` and an `in_person` block, so you can filter, report and reconcile by store, and see the same customer across channels, without a separate integration.

| Field | What it carries |
| --- | --- |
| `id` | Created by the POS terminal when the sale starts; the same ID the checkout system received |
| `channel` | `IN_PERSON` for every sale taken on a POS terminal; online payments keep their current channel |
| `customer_payer` | The Yuno customer the card belongs to, the same one you see in online payments |
| `payment_method.detail.card` | Entry mode (`CHIP`, `CONTACTLESS`), how the cardholder was verified, instalments, authorisation code, masked card, the card's payment account reference and the EMV application |
| `in_person` | Where and when: store, terminal, lane, business date, batch, and which rule chose the acquirer |
| `transactions[].provider_data` | The acquirer's identifiers (STAN, RRN, merchant and terminal ID) and its raw response code, used for reconciliation |
| `merchant_order_id` | The reference your checkout system sent, so you can join the payment to your own order |

The PIN, the full card number, the expiry date and the card's cryptogram never reach your checkout system or your servers.

## One customer, in store and online

Every card carries a payment account reference (PAR): an identifier of the card account that is not the card number and is safe to store. Yuno reads it on the POS terminal and on online payments, and links both to the same `customer_payer`. For you this means:

- You know who pays in store: repeat customers, how often they come, which stores they visit.
- In-store and online purchases of the same customer sit side by side, for loyalty, analytics and customer service.
- A refund or a dispute can be traced to the customer, whatever the channel of the original purchase.
- A returning customer can tap the card they enrolled with and the sale is charged to the account already on file, with nothing to key in.

The link is made on card data only; to attach your own customer ID to an in-store sale, send it in the sale's metadata from your checkout system.

## Subscriptions started in store

A customer can start a subscription at the counter. Your checkout system sends the subscription plan with the sale; the POS terminal takes the first payment and asks the customer to accept that the card is kept for the next charges. Yuno stores the card as a token (never the card number on your side), creates the subscription on the same account, and runs the following charges online, like any Yuno subscription. The in-store payment and the online charges share the same `customer_payer` and appear together in the dashboard.

## Statuses

| `status` / `sub_status` | Meaning |
| --- | --- |
| `SUCCEEDED` / `APPROVED` | Authorised by the acquirer |
| `DECLINED` / `DECLINED` | The issuer or acquirer declined; `response_code` carries the reason |
| `CANCELED` / `ABORTED` | Cancelled before the card was read; nothing reached an acquirer |
| `ERROR` / `REVERSED_BY_TIMEOUT` | No answer in time; the terminal reversed with the same acquirer; no charge stands (`PENDING_REVERSE` while the reversal is being confirmed) |
| `CANCELED` / `CANCELED` | Voided before the batch closed |
| `REFUNDED` / `REFUNDED` | Fully refunded |
| `SUCCEEDED` / `PARTIALLY_REFUNDED` | Part of the amount was refunded |

## Decline reasons

Each acquirer's response code (ISO 8583 field 39) is mapped to Yuno's `response_code`, the same catalogue as online. The original value stays in `provider_data.iso8583_response_code`. The ones cashiers see most:

| `response_code` | ISO 8583 | What the cashier does |
| --- | --- | --- |
| `DO_NOT_HONOR` | 05 | Ask for another card |
| `INSUFFICIENT_FUNDS` | 51 | Ask for another card or a lower amount |
| `EXPIRED_CARD` | 54 | Ask for another card |
| `INCORRECT_PIN` | 55 | Start a new sale so the customer can enter the PIN again |
| `PIN_TRIES_EXCEEDED` | 75 | Ask for another card; the card is blocked for PIN |
| `PIN_REQUIRED` | 65 | Contactless declined: insert the card and enter the PIN |
| `PROVIDER_TIMEOUT` | 68 or no answer | Nothing charged; try again |

## List in-person payments

The payments list filters by channel, store, terminal and business date, so a store's day is one call.

```bash List a store's in-person payments
curl "https://api.y.uno/v1/payments?account_id=<account_id>&channel=IN_PERSON&store_id=<store_id>&business_date=2026-10-14" \
  -H "public-api-key: $PUBLIC_API_KEY" \
  -H "private-secret-key: $PRIVATE_SECRET_KEY"
```

## Events

Your existing webhook endpoint receives in-store payments with no change: same envelope, same signature (`x-hmac-signature`), same retries. Filter on `data.payment.channel` if you want to treat them differently.

| Event (`type_event`) | When | Notes |
| --- | --- | --- |
| `payment.purchase` | A sale finished, approved or declined | Same as online; read `status` and `sub_status` |
| `payment.cancel` | A sale was voided | Same as online |
| `payment.refund` | A refund was taken, at the terminal or from the dashboard or API | Same as online |
| `payment.reverse` | A timed-out authorisation was reversed | In-person. No charge stands |
| `terminal.online` / `terminal.offline` | A POS terminal's connection to Yuno changes | In-person. Also visible in the dashboard |
| `terminal.app_updated` | A POS terminal installed a new app version | In-person |
| `host.degraded` / `host.recovered` | An acquirer's timeouts or errors cross the threshold, or recover | In-person. Terminals stop choosing an acquirer that is down |
| `batch.closed` | A batch closed at the acquirer | In-person. Carries the terminal's and the acquirer's totals |
| `reconciliation.difference_detected` | A settlement file left a difference for a store and acquirer | In-person |

## Delivery and idempotency

- Events are signed and retried the same way as your online webhooks; de-duplicate on the payment's `idempotency_key`.
- When a POS terminal couldn't reach Yuno, its sales are reported when it reconnects, with their original `created_at`. Each sale keeps the ID the terminal gave it, so a repeated report never creates a second payment.
- Order of arrival is not guaranteed across terminals; order per payment is.
