Six steps from your Yuno account to a first sale on a POS terminal. Most are configuration with your Yuno contact; the only code is on your side of the [integration type](/docs/in-person/ways-to-integrate) you choose.

  <img src="/images/in-person/setup-model.svg" alt="Set-up model: one Yuno account holds stores; each store has your contract with each acquirer; each POS terminal carries a TID and a PIN key per acquirer; one checkout system is paired per POS terminal" />
</Frame>

<Steps>
  <Step title="Use your Yuno account">
    In-person payments live in the same account, API keys and dashboard as your online payments. Nothing new to create. If you are new to Yuno, [set up your account](https://docs.y.uno/docs/how-yuno-works/step-1-set-up-your-account) first.
  </Step>
  <Step title="Register stores, acquirers and POS terminals">
    Each store gets an identifier, and for each store you register the acquirers you work with and the merchant ID each one gave you. Yuno integrates and certifies the acquirer; the contract with it is yours.
    Each lane gets a POS terminal, and each terminal gets the terminal ID (TID) that each acquirer issues for it. Registration happens in the dashboard, or from a list of serial numbers for large fleets. Only registered terminals can talk to Yuno.
  </Step>
  <Step title="Install the Yuno Payment App and the keys">
    The app is signed through the terminal vendor's signing process and distributed through the vendor's estate manager or your own device management. Each acquirer's PIN key is injected by that acquirer or by the vendor, never by Yuno. See [POS terminals and fleet](/docs/in-person/terminals).
  </Step>
  <Step title="Set routing rules">
    Which acquirers each store can use and how to choose between them: store, amount, payment method, acquirer health. Enable instalment plans, payment methods and your brand for the terminal screens. The configuration reaches each terminal when it next connects.
  </Step>
  <Step title="Connect your checkout system">
    For the Local type, each lane's checkout system is paired once with its POS terminal so that only it can start sales there. For the Cloud type, your server calls the Payments API. See [Connect your checkout system](/docs/in-person/connect-your-checkout-system).
  </Step>
  <Step title="Test in sandbox, then go live">
    Sandbox terminals run the same app against Yuno's acquirer simulator, with test cards that produce approvals, declines and timeouts on demand. Switch a store to live when its terminals report online and a test sale reconciles. See [Testing](/docs/in-person/get-started#testing) below.
  </Step>
</Steps>

## What you build

All four integration types work today and share the same payment, webhooks, dashboard and reconciliation. You can run more than one: for example Local in your stores and Standalone as the fallback on the same terminal.

| Integration type | What it is | What you build | What Yuno provides |
| --- | --- | --- | --- |
| **Local** | Your checkout system sends the amount to the POS terminal in the store, over the store network or a cable, and gets the result back to print | The calls on your checkout system: sale, void, refund, status, recovery ([Connect your checkout system](/docs/in-person/connect-your-checkout-system)) | The Yuno Payment App, routing, acquirer integrations, payment record, webhooks, reconciliation |
| **Cloud** | Your server creates the in-person payment through the Payments API; Yuno sends it to a POS terminal in that store and you get the result by webhook | One API call and a webhook handler, which you likely already have for online | The same, plus the delivery of the sale to the terminal |
| **Standalone** | The cashier keys the amount on the POS terminal; no integration at all | Nothing | The same |
| **Reconciliation first** | Yuno reconciles the sales of your current terminals against your acquirers' settlement files, before any terminal runs the Yuno Payment App | Access to your acquirers' settlement files and an export of your current sales | Matching per store and acquirer, and the reconciliation views |

## Testing

- **Sandbox terminals.** A registered POS terminal can be switched to sandbox: the same app, the same screens, against Yuno's acquirer simulator instead of the acquirer. No real money moves.
- **Test cards.** A set of test cards produces a fixed outcome each: approved, declined with a given reason, timeout, instalments offered or not. Ask your Yuno contact for the set.
- **Webhooks.** Sandbox sales send the same events as live ones, so your handler can be tested end to end before the first store goes live.
- **Reconciliation.** The simulator produces a settlement file for sandbox sales, so the reconciliation view can be checked before real files arrive.

Before going live, run at least these cases from your checkout system: approved sale, declined sale, sale cancelled before the card, acquirer timeout (reversed), void, full and partial refund, instalment sale, batch close, and a checkout restart in the middle of a sale (your checkout system must recover the result, not charge again).

## Go-live checklist

- POS terminals report online in the fleet view, with the expected app version.
- Each terminal has a TID and a key for every acquirer its store can route to.
- Every lane's checkout system is paired with its POS terminal (Local type).
- A sale on each integration type you use reaches your webhook with `channel: IN_PERSON`.
- Routing rules for the store are published.
- Each acquirer ran its acceptance tests with you: sale, void, refund and batch close.
- A sandbox sale reconciled; the acquirer's live settlement file delivery is confirmed.
- Receipts print with the text you configured.
