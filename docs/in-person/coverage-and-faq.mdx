## Coverage

|  |  |
| --- | --- |
| **Regions** | Latin America and Europe. Each country is its own certification chain, with its own acquirers and local schemes, so tell your Yuno contact which markets you need and they will confirm the chain for each. |
| **Acquirers** | The acquirers you already work with. Yuno integrates and certifies the Yuno Payment App with each new acquirer on demand, following the acquirer's specification. |
| **Card brands** | Visa and Mastercard; other card schemes on demand. |
| **POS terminals** | Android POS terminals that accept external payment applications, from vendors such as Ingenico and Verifone. A new vendor is an adapter to the same app; confirm your models with your Yuno contact. |
| **Payment methods** | Chip and PIN, contactless and instalments. Local methods such as QR payments and wallets are added per market, each following its provider's API specification. |
| **Integration types** | Local, cloud, standalone and reconciliation first, all on the same payment, the same certified app and the same reconciliation. |
| **Beyond the sale** | Reconciliation per store and acquirer, subscriptions started in store, and one customer view across in-store and online. The fields these need are in the certified message from day one, so switching them on is never a recertification. |

## Certification and compliance

|  | What it is | Where Yuno stands |
| --- | --- | --- |
| **EMV Level 1 and 2** | The terminal hardware and kernel, approved by EMVCo | The vendor's, unchanged: the Yuno Payment App uses the kernel through the vendor's SDK and never modifies it |
| **Level 3 / card-brand certification** | The full chain terminal, app, Yuno Cloud and acquirer, tested end to end per acquirer and brand (Mastercard M-TIP, Visa) | Yuno certifies the chain with each acquirer, which signs the certification. Adding an acquirer is a new host certification; adding a merchant is not, and the terminal app is not rebuilt |
| **Service provider registration** | Each acquirer registers the providers in its chain with Visa and Mastercard | Done by each acquirer for Yuno |
| **PCI PTS** | The PIN pad hardware | The vendor's, unchanged |
| **PCI DSS** | How Yuno handles card data | In-person payments run inside Yuno's PCI DSS programme, extended to card-present data |
| **PCI PIN** | Transmitting, decrypting or translating PINs | Yuno is in scope and is certifying. The terminal encrypts the PIN under Yuno's key; Yuno translates it to the chosen acquirer's key inside a hardware security module, so the PIN is never in the clear anywhere. This is what lets the acquirer be chosen after the card is read, and it gates the pilot |
| **PCI Secure Software** | How the payment application is built and released | The Yuno Payment App is built and released under the PCI Software Security Framework, certified as part of the same programme as PCI PIN |

What restarts certification and what doesn't is on [POS terminals and fleet](/docs/in-person/terminals).

## FAQ

<AccordionGroup>
  <Accordion title="Do we need to buy new POS terminals?">
    Not if your terminals are Android devices whose vendor allows external payment applications. If you are mid-migration to a new fleet, that is the easiest moment to add the app. Yuno doesn't sell or lease terminals.
  </Accordion>
</AccordionGroup>

<AccordionGroup>
  <Accordion title="What is the difference between the POS terminal and the checkout system?">
    The POS terminal is the card device on the counter, where the Yuno Payment App runs and the customer taps or inserts the card. The checkout system is your cash-register software, where the cashier rings up the basket and which tells the terminal how much to charge. In the Standalone type there is no checkout system involved: the cashier keys the amount on the terminal.
  </Accordion>
</AccordionGroup>

<AccordionGroup>
  <Accordion title="Do we need to change acquirers?">
    No. You keep your contracts, your merchant IDs and your rates. Yuno routes between the acquirers you work with; if one is not integrated yet, Yuno integrates and certifies it on demand.
  </Accordion>
</AccordionGroup>

<AccordionGroup>
  <Accordion title="Our POS terminals came from our acquirer. Can we use them?">
    Only with that acquirer's agreement: a terminal an acquirer provides is usually locked to its own payment application. By default Yuno runs on vendor-agnostic Android terminals you own, bought from the vendor rather than from an acquirer, so the same fleet can route to several acquirers. If your fleet came from an acquirer, tell your Yuno contact which acquirer and which models and they will check what is possible before you plan a rollout.
  </Accordion>
</AccordionGroup>

<AccordionGroup>
  <Accordion title="Why is the sale authorised through Yuno Cloud and not from the terminal?">
    Because that is what lets one fleet reach several acquirers without a key, an integration and a certification per acquirer on every terminal. The terminal holds one key, Yuno's, and sends one message; Yuno Cloud chooses the acquirer for that sale, translates the PIN in a hardware security module and speaks each acquirer's dialect. Adding an acquirer is then a change in Yuno Cloud, not a new app in the field. The trade is real and deliberate: a card sale through Yuno needs the link to Yuno Cloud.
  </Accordion>
</AccordionGroup>

<AccordionGroup>
  <Accordion title="Does Yuno touch the card data or the PIN?">
    The card is read and the PIN is entered on the terminal's certified hardware and encrypted under Yuno's key. Yuno translates the PIN to the chosen acquirer's key inside a hardware security module: it is never in the clear, inside Yuno or anywhere else, and no person at Yuno can see it. This is why Yuno is in PCI PIN scope and certifies for it. Card data only leaves the terminal encrypted, and it is kept only as a token when the customer agrees to a subscription.
  </Accordion>
</AccordionGroup>

<AccordionGroup>
  <Accordion title="What happens if the store loses its connection to Yuno?">
    A card sale through Yuno cannot be authorised, so the terminal declines cleanly, before the card is read where it can, and nothing is charged. There is no store-and-forward: a sale is never taken on the promise of authorising it later, because that promise is the merchant's loss when the card turns out to be bad. Yuno Cloud runs in two regions and the terminal keeps the link open, so a drop is known before a sale starts and the cashier can take cash or another tender.
  </Accordion>
</AccordionGroup>

<AccordionGroup>
  <Accordion title="Can a declined payment be retried with another acquirer?">
    Not in store. One sale is one authorisation, and an issuer decline is final: the customer is standing there and a second attempt is theirs to make. A sale is resent to a second acquirer in one case only, when the first acquirer's host failed before the issuer ever saw it. Routing across sales is where the benefit is: cost, instalment programmes and staying up when an acquirer is down.
  </Accordion>
</AccordionGroup>

<AccordionGroup>
  <Accordion title="Do voids and refunds follow the routing rules?">
    No. They always go to the acquirer that approved the original sale.
  </Accordion>
</AccordionGroup>

<AccordionGroup>
  <Accordion title="Can we see the same customer in store and online?">
    Yes. In-store and online payments made with the same card link to the same customer through the card's payment account reference, without the card number reaching your systems. The reference is carried on every in-store sale from day one. See [Payments and events](/docs/in-person/payments-and-events).
  </Accordion>
</AccordionGroup>

<AccordionGroup>
  <Accordion title="Can a customer pay part with one card and part with another?">
    Yes. Each card is its own payment, sent one after the other with the same order reference. Each is routed and authorised on its own; if the second declines, the first stands.
  </Accordion>
</AccordionGroup>

<AccordionGroup>
  <Accordion title="We are a platform and our merchants own the terminals. How do we integrate?">
    With the Cloud type: your server creates the sale and a registered POS terminal in the store collects it. Reconciliation first can connect your merchants' acquirers before their terminals switch.
  </Accordion>
</AccordionGroup>
