title: "Capability matrix"
description: "A single reference mapping common vendor/RFP capability names to the Yuno feature that implements them, for buyer evaluations and capability checklists."
---

Buyers evaluating Yuno often paste a vendor capability checklist, a list of generic,
RFP-style capability names rather than Yuno's own terminology, and ask whether each one is
supported. This page maps those common capability names to the actual Yuno feature, so the
answer always points back to one authoritative source instead of being assembled differently
each time.

If a capability you're evaluating isn't listed here, treat it as **not yet confirmed** rather
than unsupported. Ask your Yuno contact directly.

## Access and account management

| Capability | Supported | How Yuno implements it | Docs |
| --- | --- | --- | --- |
| Entitlement management (defining and controlling access permissions across identities and systems) | Yes | Teams and roles: predefined and custom roles, assignable at account or organization level, with independent Sandbox/Production access | [Roles](/docs/using-yuno/organization/roles), [Team Members](/docs/using-yuno/organization/team-members) |

## Fraud, risk, and payment method eligibility

| Capability | Supported | How Yuno implements it | Docs |
| --- | --- | --- | --- |
| Fraud engine orchestration (coordinating decisioning across multiple fraud/risk providers in one flow) | Yes | Routing's risk profile rule engine lets you chain multiple fraud and 3DS/authentication connections into one decision flow, with sequencing and branch-based outcomes | [Risk Conditions](/docs/using-yuno/dashboard-overview/risk-conditions), [Routing](/docs/using-yuno/dashboard-overview/routing) |
| Payment method eligibility resolution (showing only payment methods valid for a given transaction) | Yes | Checkout Builder conditions filter payment methods by country, currency, order value, and integration metadata; only connected and configured methods are ever eligible | [Checkout Builder](/docs/using-yuno/dashboard-overview/checkout-builder) |

## Checkout and PCI scope

| Capability | Supported | How Yuno implements it | Docs |
| --- | --- | --- | --- |
| Drop-in / embeddable checkout (pre-built UI, minimal custom development, reduced PCI scope) | Yes | Yuno's SDKs render payment fields inside Yuno's secure environment; merchants receive tokens only, typically qualifying for SAQ A | [PCI Compliance](/docs/security-and-compliance/pci-compliance) |
| Vault-and-forward proxy (tokenizing a credential at collection and forwarding it downstream without exposing raw data) | Yes | Forward Proxy lets you call Yuno with vaulted tokens, builds the destination request with vaulted-token expressions, and redacts card data in responses | [Forward Proxy](/docs/security-and-compliance/pci-proxy/forward-proxy) |
| Installment plan presentation (showing available installment/BNPL options before purchase) | Yes | SDK integrations show the installment selector automatically once a provider connection has installments enabled and a plan is configured | [Merchant Installments](/docs/payment-features/installments/merchant-installments), [Provider Installments](/docs/payment-features/installments/provider-installments) |

## Transaction and billing identifiers

| Capability | Supported | How Yuno implements it | Docs |
| --- | --- | --- | --- |
| Merchant descriptor configuration (controlling the text shown on a cardholder's statement) | Yes | Set `soft_descriptor` once on a subscription for recurring rebills, or per payment under `payment_method.detail.*.soft_descriptor` for merchant-initiated charges | [Statement Descriptor](/docs/payment-features/subscriptions/soft-descriptor) |
| Transaction identifier management (linking unique IDs across systems for reconciliation, disputes, and audit trails) | Yes | Customers, checkout sessions, and payments are chained with Yuno-generated identifiers; `merchant_reference` is preserved end-to-end for reconciliation and chargebacks | [Payment Flow](/docs/how-yuno-works/how-yuno-payment-flow-works), [API Enums & Identifiers](/reference/api-enums), [Chargeback Management](/docs/payouts-and-disputes/chargeback-management) |

## Marketplace and sub-merchants

| Capability | Supported | How Yuno implements it | Docs |
| --- | --- | --- | --- |
| Sub-merchant onboarding (registering and activating sub-merchants under a master account) | Yes | Sub-merchants are modeled as recipients in the Split Payments Marketplace model, created via the Recipients API and onboarded (pre-onboarded or through a provider flow) | [Split Payments Marketplace](/docs/payment-features/split-payments-marketplace), [Onboarding Statuses](/reference/recipients-for-marketplace/onboarding-statuses-and-response-codes) |
| Split payments to multiple sub-merchants | Yes | The `split_marketplace` object splits a payment across recipients, with absolute or percentage splits and multiple item types (purchase, commission, fees, VAT) | [Split Payments Marketplace](/docs/payment-features/split-payments-marketplace) |
| Sub-merchant payouts | Yes | Standalone/Forward Transfer distributes proceeds to recipients independently of a specific payment; Yuno Payouts can also send funds to beneficiaries directly | [Split Payments Marketplace](/docs/payment-features/split-payments-marketplace), [Payouts](/docs/payouts-and-disputes/payouts) |
| Multi-seller / franchise routing (routing a payment to the correct merchant ID per seller) | Yes | Register seller mappings and pass `seller_id`/`merchant_seller_id` in `additional_data.seller_details`; Yuno resolves the correct `merchant_id` at payment time, falling back to the connection default if no mapping is found | [Manage Sellers](/reference/sellers/manage-sellers), [Using Sellers in Payments](/reference/sellers/using-sellers-in-payments) |

## Needs confirmation

feature yet. Check with your Yuno contact rather than assuming either way:

  underlying payment provider's support for split chargebacks, not just Yuno's orchestration).
