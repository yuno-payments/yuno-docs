---
title: "Referência dos campos da afiliação"
description: "Todos os campos do formulário do provedor Yuno na VTEX, com formato, valor padrão, versão mínima do plugin e um exemplo."
---

Estes são os campos do formulário do provedor Yuno na VTEX, em **Store Settings → Payment → Providers**, na sua afiliação da Yuno. O [guia de configuração](/pt-br/docs/plugins/vtex/set-up-yuno-on-vtex) mostra onde fica o formulário e quais campos a própria VTEX adiciona a ele.

## Affiliation Name {#affiliation-name}

Um nome legível para esta integração da Yuno.

- **Obrigatório**: Sim

Você vê este nome ao escolher o provedor em uma condição de pagamento, então escolha um nome que diferencie suas afiliações, por exemplo pelo país ou pela conta da Yuno por trás dela.

**Exemplo**: `Yuno Brazil`

## Account ID {#account-id}

O seu **Account ID** da Yuno.

- **Obrigatório**: Sim

Encontre-o no Dashboard da Yuno, em **Developers → API Credentials**.

**Exemplo**: `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`

## Public API Key {#public-api-key}

A sua **Public API Key** da Yuno.

- **Obrigatório**: Sim

Encontre-a no Dashboard da Yuno, em **Developers → API Credentials**. O prefixo dela define o ambiente da Yuno que a loja usa: `dev_`, `staging_`, `sandbox_` ou `prod_`.

**Exemplo**: `sandbox_pub-xxxxxxxx`

## Private Secret Key {#private-secret-key}

A sua **Private Secret Key** da Yuno.

- **Obrigatório**: Sim

Encontre-a no Dashboard da Yuno, em **Developers → API Credentials**. Ela precisa pertencer à mesma conta e ao mesmo ambiente da Public API Key.

**Exemplo**: `xxxxxxxxxxxxxxxxxxxxxxxx`

## Main Account Name {#main-account-name}

A conta VTEX dona dos dados dos pedidos, em configurações com várias contas.

- **Obrigatório**: Não. Deixe vazio em uma loja com uma única conta.

O plugin lê os pedidos e os grupos de pedidos desta conta. Configure-o junto com **Main Account App key** e **Main Account App token**: se qualquer um dos três estiver vazio, o plugin ignora todos eles. Veja [Multiconta](/pt-br/docs/plugins/vtex/advanced-features#multi-account) para saber quais configurações precisam dele.

**Exemplo**: `mystoreparent`

## Main Account App key {#main-account-app-key}

Application Key da conta VTEX principal.

- **Obrigatório**: Não. Somente com **Main Account Name**.

O plugin a usa para chamar as APIs da VTEX em nome da conta principal. Veja [Multiconta](/pt-br/docs/plugins/vtex/advanced-features#multi-account).

**Exemplo**: `vtexappkey-mystoreparent-XXXXXX`

## Main Account App token {#main-account-app-token}

Application Token da conta VTEX principal.

- **Obrigatório**: Não. Somente com **Main Account Name**.

Ele forma par com **Main Account App key**. Veja [Multiconta](/pt-br/docs/plugins/vtex/advanced-features#multi-account).

**Exemplo**: `XXXXXXXXXXXXXXXXXXXXXXXX`

## Soft Descriptor {#soft-descriptor}

Texto personalizado que aparece na fatura do cartão do comprador.

- **Obrigatório**: Não

**Exemplo**: `MYSTORE*ORDER`

## Create Customer {#create-customer}

Cria um registro de cliente na Yuno para cada comprador.

- **Obrigatório**: Não

Quando configurado como **Yes**, o plugin cria um registro de cliente correspondente na Yuno. **Vault Card for Order Modification** e **Enable Network Tokens** precisam dele.

**Exemplo**: `Yes`

## VTEX IO orderPlaced page URL {#vtex-io-orderplaced-page-url}

Para onde os compradores vão depois do pagamento.

- **Obrigatório**: Não

Uma URL personalizada para a qual os compradores são redirecionados depois do pagamento.

**Exemplo**: `https://www.example.com/checkout/orderPlaced`

## Payment Mode {#payment-mode}

Como o comprador paga: dentro do checkout ou em uma página de redirecionamento.

- **Obrigatório**: Não

Escolha **Payment App** para exibir o pagamento dentro do checkout da VTEX, ou **Legacy** para lojas no checkout Legacy da VTEX, que não consegue exibir um Payment App: nesse caso, o comprador é redirecionado para uma página de pagamento hospedada pela Yuno. Padrão: **Payment App**.

**Exemplo**: `Payment App`

## Transaction Identification From {#transaction-identification-from}

Qual ID de transação o pedido mostra.

- **Obrigatório**: Não

Escolha **Yuno TID** para mostrar o ID de transação da Yuno, ou **Provider TID** para mostrar o ID de transação atribuído pelo provedor de pagamento que processou o pagamento. Quando o provedor não envia um ID de transação, o ID da Yuno é mostrado. Padrão: **Yuno TID**.

**Exemplo**: `Yuno TID`

## Antifraud Providers for Split Orders {#antifraud-providers-for-split-orders}

Quais provedores antifraude recebem a sessão compartilhada em pedidos divididos.

- **Obrigatório**: Não
- **Padrão**: os quatro provedores no plugin **4.2.362 ou posterior**; `RISKIFIED` e `CYBERSOURCE` nas versões anteriores.

Escreva uma lista separada por vírgulas com valores entre `RISKIFIED`, `CYBERSOURCE`, `SIGNIFYD` e `CIELO_CYBERSOURCE_FRAUD`. Se você preencher o campo, só os provedores listados recebem a sessão.

**Exemplo**: `RISKIFIED,CYBERSOURCE`

## Vault Card for Order Modification {#vault-card-for-order-modification}

Permite que o plugin cobre a diferença quando o total de um pedido aumenta.

- **Obrigatório**: Não. Precisa de **Create Customer** configurado como **Yes**.

Quando configurado como **Yes**, o plugin armazena com segurança o cartão usado em cada pedido e cobra automaticamente o valor adicional se o total do pedido aumentar depois. Este é o único campo que autoriza cobranças adicionais: quando está como **No**, um aumento no total do pedido é recusado mesmo que o cartão tenha sido armazenado para network tokens. Veja [Modificações de pedido](/pt-br/docs/plugins/vtex/advanced-features#order-modifications-changed-order-totals).

**Exemplo**: `Yes`

## Enable Network Tokens {#enable-network-tokens}

Armazena cartões para que compras recorrentes possam usar um network token.

- **Obrigatório**: Não. Precisa de **Create Customer** configurado como **Yes**.

Quando configurado como **Yes**, o plugin armazena com segurança cada cartão na primeira compra e o reconhece nas compras seguintes do mesmo cliente, para que a Yuno possa processar as compras recorrentes com um network token em vez do número do cartão.

<Warning>
  A opção não tem efeito até que a Yuno ative os network tokens nas rotas que a sua loja usa. Até lá, os cartões são armazenados, mas nenhum token é emitido. Entre em contato com o seu KAM da Yuno ou com o suporte para ativar.
</Warning>

Veja [Network tokens](/pt-br/docs/plugins/vtex/advanced-features#network-tokens-repeat-card-purchases).

**Exemplo**: `Yes`

## Use Corporate Buyer Data {#use-corporate-buyer-data}

Paga pedidos de empresas em nome da empresa e com o CNPJ dela. Somente no Brasil.

- **Obrigatório**: Não
- **Padrão**: `No`

Quando configurado como **Yes**, os pedidos feitos por um comprador que finaliza a compra como empresa (*pessoa jurídica*) são pagos com a razão social e o **CNPJ** da empresa, em vez do nome pessoal e do CPF do comprador, em todos os meios de pagamento. Veja [Compras corporativas](/pt-br/docs/plugins/vtex/advanced-features#corporate-purchases-brazil).

**Exemplo**: `Yes`

## Headless Payment Handoff {#headless-payment-handoff}

Para marketplaces cujo próprio checkout headless cria o pagamento na Yuno.

- **Obrigatório**: Não
- **Padrão**: `No`
- **Disponível no plugin**: **4.2.356 ou posterior** para cartões, **4.2.361 ou posterior** para PIX

Esta é uma configuração avançada para marketplaces que operam o próprio checkout headless e criam eles mesmos o pagamento na Yuno, para um carrinho que mistura itens da própria loja e de sellers do marketplace da VTEX. Ative-a somente com a orientação da equipe da Yuno.

Quando configurado como **Yes**, o plugin não cria nada na Yuno. Cada autorização entrega a você uma requisição de pagamento da Yuno pronta para envio, somente de autorização, para a parte VTEX do carrinho. Você adiciona o token do cartão e o split do marketplace, e cria um único pagamento que cobre todos os pedidos de sellers do carrinho. Em seguida, o plugin informa o status de cada pedido a partir desse pagamento e captura ou reembolsa a parte de cada pedido separadamente.

Somente cartões e PIX: qualquer outro meio de pagamento é recusado.

**Exemplo**: `Yes` na loja que opera o checkout headless. Todas as outras lojas mantêm `No`.

## Store Base Path {#store-base-path}

O prefixo de caminho da URL de uma loja que não é servida a partir da raiz do domínio.

- **Obrigatório**: Não
- **Disponível no plugin**: **4.2.316 ou posterior**

Use-o para uma loja virtual em `https://www.example.com/br` em vez da raiz do domínio. É o caminho que o Payment App usa quando chama as rotas de pagamento da sua loja durante o checkout. Deixe vazio quando a loja é servida a partir da raiz do domínio.

- Use apenas segmentos de caminho simples: letras, números, `-` e `_`. Sem esquema, host, query string ou pontos.
- Uma barra inicial é adicionada se estiver faltando.
- Um valor que parece um nome de host é ignorado, e a loja se comporta como se o campo estivesse vazio.

**Exemplo**: `/br` ou `/br/store`

## Send Order Sequence as Merchant Reference {#send-order-sequence-as-merchant-reference}

Envia a sequência do pedido VTEX como a referência do lojista do pagamento.

- **Obrigatório**: Não
- **Padrão**: `No`
- **Disponível no plugin**: **4.2.333 ou posterior** para PIX, boleto e os outros meios criados no servidor; **4.2.355 ou posterior** para todos os meios de pagamento

Quando configurado como **Yes**, todo pagamento envia a sequência do pedido VTEX (o número mostrado na lista de pedidos da VTEX, por exemplo `1234567890123`) como a referência do lojista do pagamento. Um provedor configurado com uma identificação de transação personalizada, como o Mercado Pago, passa então a mostrar essa sequência como a referência externa no painel dele, como fazia antes da sua migração para a Yuno.

Quando configurado como **No**, ou quando a sequência não está disponível, a referência é o ID do pedido VTEX.

**Exemplo**: `Yes`

## Sales Channel Domains {#sales-channel-domains}

Associa cada canal de vendas ao domínio da sua loja virtual.

- **Obrigatório**: Não
- **Disponível no plugin**: **4.2.333 ou posterior**

Associa o ID de cada canal de vendas (política comercial) da VTEX ao domínio público da sua loja virtual, para que o pagamento informe a loja virtual de onde veio o pedido em vez do host padrão da conta. Isso melhora os relatórios e a conciliação em lojas que operam várias lojas virtuais em uma única conta.

- Escreva pares `id=domain` separados por `;`. Uma `,` entre os pares e um `:` entre o ID e o domínio também são aceitos.
- Um prefixo `https://` e barras finais são removidos, e pares malformados são ignorados.
- Os canais de vendas que você não lista usam o host da loja virtual do próprio pedido. Lojas que deixam o campo vazio mantêm o comportamento atual.

**Exemplo**:

```text
1=www.example.com;2=b2b.example.com;18=members.example.com
```

## Delay To Cancel {#delay-to-cancel}

Quanto tempo a VTEX espera por um pagamento pendente, por meio de pagamento, antes de cancelar o pedido.

- **Obrigatório**: Não
- **Padrão**: a janela de cada meio de pagamento, listada em [Quanto tempo a VTEX espera por um pagamento pendente](#how-long-vtex-waits-for-a-pending-payment)
- **Disponível no plugin**: **4.2.373 ou posterior**; o par `Pix`, **4.2.379 ou posterior**

Quando um pagamento ainda está pendente, a VTEX espera um tempo definido antes de cancelar o pedido e liberar o estoque dele. Este campo define esse tempo por meio de pagamento.

- Escreva pares `Method=seconds` separados por `;`. Uma `,` entre os pares e um `:` entre o nome e os segundos também são aceitos.
- `Method` é o nome do meio de pagamento como ele aparece quando você cria uma condição de pagamento na VTEX (por exemplo `Mastercard`, `MercadoPagoPro` ou `Pagaleve Transparente`), não o nome que você dá à condição. A lista completa está em [Meios de pagamento que você pode configurar no Delay To Cancel](#payment-methods-you-can-set-in-delay-to-cancel).
- Os nomes são comparados sem diferenciar maiúsculas de minúsculas, mas os acentos precisam coincidir, como em `Elo Débito`.
- `Cards` se aplica a todas as bandeiras de cartão, e o par próprio de uma bandeira prevalece sobre `Cards`.
- Os segundos precisam ser um número inteiro entre `600` (10 minutos) e `2592000` (30 dias). Um par fora desse intervalo, ou um par malformado, é ignorado, e o meio mantém o padrão dele.
- Os cartões e os meios exibidos pela Yuno (Apple Pay, Google Pay, Samsung Pay, Click to Pay) nunca esperam menos de uma hora: um valor menor passa a ser uma hora.
- Para cartões, o valor também substitui a janela de 3 dias de um pagamento com cartão que já existe e ainda está pendente (revisão antifraude ou desafio do cartão). Por isso, um valor curto cancela revisões que teriam sido aprovadas mais tarde.
- `Pix` define a janela do PIX no checkout com Payment App, dentro dos [limites de PIX da VTEX](https://developers.vtex.com/docs/api-reference/payment-provider-protocol#post-/payments) de 15 minutos a 1 hora. De `900` a `3600`, o valor é usado como escrito; de `600` a `899`, passa a ser 15 minutos; e acima de `3600`, passa a ser 1 hora. Sem um par `Pix`, ou com um valor abaixo de `600`, que é ignorado como qualquer outro par, a janela é de 1 hora.
- O Boleto Bancário não pode ser configurado: ele segue a data de vencimento.
- No headless payment handoff, a partir do plugin **4.2.376**, o PIX sempre espera 15 minutos, quando o QR code dele expira, e os cartões esperam o par `Cards` ou o da bandeira (pelo menos 1 hora) ou 24 horas sem nenhum deles.

**Exemplo**: os cartões esperam 3 dias e o PIX, 15 minutos.

```text
Cards=259200;Pix=900
```

### Expiração do QR code do PIX {#pix-qr-code-expiration}

No checkout com Payment App, o plugin pede ao provedor um QR code do PIX que expira junto com a janela do PIX, para que o QR code deixe de poder ser pago quando a VTEX cancelar o pedido não pago. O que você configura depende de o provedor respeitar ou não essa expiração.

| Provedor | Expiração do QR code | O que configurar |
| :--- | :--- | :--- |
| Mercado Pago, PagBank | A janela do PIX. Ela substitui a expiração definida na conexão do provedor, inclusive quando a da conexão é menor: um QR code de 15 minutos passa a ser de 1 hora. | Para manter um QR code menor que 1 hora, defina um par `Pix`, por exemplo `Pix=900`. |
| Pagar.me | A janela do PIX; se a conexão tiver `Transactions expire time` definido, a menor das duas. | Defina um par `Pix` ou `Transactions expire time` para encurtá-la. |
| Santander, PicPay, Itaú, Pinbank, Pay4Fun, dLocal | A expiração definida na conexão do provedor; o par `Pix` não chega ao QR code. A VTEX espera essa expiração, entre 15 minutos e 1 hora, ou a janela do PIX quando o provedor não informa nenhuma expiração. | Defina a expiração do PIX da conexão em 60 minutos ou menos. Um QR code mais longo ainda pode ser pago depois que a VTEX cancela o pedido. |

O checkout de redirecionamento (Legacy) e o Pagaleve Pix A Vista não usam a janela do PIX: o QR code mantém a expiração da conexão, então a mesma regra dos 60 minutos se aplica a eles.

### Quanto tempo a VTEX espera por um pagamento pendente {#how-long-vtex-waits-for-a-pending-payment}

Sem o campo **Delay To Cancel**, cada meio de pagamento usa a janela abaixo no plugin **4.2.372 ou posterior**. As versões anteriores esperavam até 24 horas para as carteiras digitais, e algumas respostas pendentes não traziam nenhuma janela. O campo substitui a janela de todos os meios, exceto o Boleto Bancário; o par `Pix` se aplica somente ao checkout com Payment App.

| Meio de pagamento | Janela padrão |
| :--- | :--- |
| Cartões e MONNET | 24 horas. Um pagamento com cartão que já existe e está em revisão (revisão antifraude ou desafio do cartão) recebe 3 dias. |
| Boleto Bancário | A data de vencimento do boleto, com mínimo de 24 horas. |
| PIX | A expiração do QR code, entre 15 minutos e 1 hora. No plugin **4.2.379 ou posterior**, os QR codes do Mercado Pago, PagBank e Pagar.me expiram depois de 1 hora por padrão; veja [Expiração do QR code do PIX](#pix-qr-code-expiration). |
| Apple Pay, Google Pay, Samsung Pay, Click to Pay e os outros meios exibidos pela Yuno, PicPay, MercadoPagoPro, Nubank, Pagaleve | 1 hora. |

No checkout de redirecionamento (Legacy), os padrões são diferentes: PIX, PicPay, MercadoPagoPro e Nubank esperam 1 hora, e todos os outros meios, inclusive o boleto, 24 horas. A partir do plugin **4.2.376**, o headless payment handoff espera 15 minutos para PIX e 24 horas para cartões.

### Meios de pagamento que você pode configurar no Delay To Cancel {#payment-methods-you-can-set-in-delay-to-cancel}

Escreva o nome exatamente como a VTEX o mostra quando você cria a condição de pagamento. Maiúsculas e minúsculas não importam; acentos e espaços, sim. Um valor abaixo da espera mínima do seu grupo é elevado a essa espera, e um valor de `Pix` acima de 1 hora é reduzido para 1 hora.

| Grupo | Nomes | Espera mínima |
| :--- | :--- | :--- |
| `Cards`, ou uma bandeira de cartão | Visa, Mastercard, American Express, Diners, Elo, Hipercard, Discover, JCB, Aura, Alelo, Privatelabels, Cobranded, Visa Electron, Débito Online, Maestro, Mastercard Debit, VirtualDebitElo, Elo Débito, Voucher. O par próprio de uma bandeira prevalece sobre `Cards`. No checkout de redirecionamento (Legacy), `Cards` também cobre o Yuno Card. | 1 hora |
| Meios exibidos pela Yuno | Apple Pay, Google Pay, Samsung Pay, C2P, Yuno C2P Golden, Fast payments with Mercado Pago, PSE, Safetypay, PagoEfectivo, Yuno Card, Yuno Wallet, Yuno Bank Transfer, Yuno Buy Now Pay Later, Yuno Payment Link, Yuno Ticket e qualquer outro nome de meio que não esteja listado aqui. | 1 hora |
| `Pix` | Pix. Somente no checkout com Payment App, plugin **4.2.379 ou posterior**. Um valor acima de 1 hora passa a ser 1 hora. | 15 minutos |
| Meios criados no servidor | Nubank, PicPay, MercadoPagoPro, Pagaleve Transparente, Pagaleve Pix A Vista Transparente, MONNET - CASH, MONNET - BANK TRANSFER. | 10 minutos |
| Não configurável | Boleto Bancário (segue a data de vencimento). No checkout de redirecionamento (Legacy), o Yuno Ticket é um boleto e também não é configurável. | |
