---
title: "Modo Render"
description: "Migre integrações Render de Android (Activity.startPaymentRender + YunoPaymentRenderListener) para a API unificada de Transaction."
---

O modo Render permite incorporar o formulário de pagamento do SDK no seu próprio layout: você chamava `startPaymentRender(…)` e recebia um `YunoPaymentFragmentController` mais um callback `YunoPaymentRenderListener.showView(fragment)` que entregava o `Fragment` do SDK. Você o posicionava no seu layout e chamava `controller.submitForm()` (ou `controller.continuePayment()` para a etapa de 3DS) a partir do seu próprio botão.

Na API unificada, o mesmo padrão é expresso sobrescrevendo [`showView`](/pt-br/docs/yuno-sdk/controllers/show-view). O SDK continua entregando a você um `Fragment`; você o recebe junto com um objeto de controle `TransactionProcess` que expõe `onSubmit()` e `onClose()`. A continuação (3DS / redirecionamento) não é mais uma chamada separada. O SDK emite um segundo `showView` com `step = ACTION` quando precisa.

## Antes de começar {#before-you-start}

- Substitua os imports `com.yuno.sdk.*`, `com.yuno.payments.features.*` e `com.yuno.presentation.*` pelos equivalentes `com.yuno.payments.sdk.api.*` (o lado a lado os lista). Sua chave de API pública e as sessões de checkout que o seu backend cria não mudam ([Antes de começar](/pt-br/docs/yuno-sdk/get-started#before-you-begin)).
- Decida quem cria o pagamento. O `workflow` da sessão de checkout deve corresponder a essa decisão:

| Quem cria o pagamento | No Render você tinha | Na API unificada | `workflow` da sessão |
|---|---|---|---|
| Seu backend | `returnOneTimeToken` implementado (a variante headless-render) | Sobrescrever `createPayment` | Padrão (`SDK_CHECKOUT`) |
| O SDK | Sem `returnOneTimeToken` | Sem sobrescrita | `SDK_SEAMLESS` |

<Warning>
Uma sessão com o workflow padrão e sem sobrescrita de `createPayment` termina em `INTERNAL_ERROR`: o backend rejeita a criação do pagamento pelo SDK. Veja [`createPayment`](/pt-br/docs/yuno-sdk/controllers/create-payment).
</Warning>

## Lado a lado {#side-by-side}

<CodeGroup>

```kotlin Before. Render mode
import androidx.fragment.app.Fragment
import com.yuno.sdk.payments.render.startPaymentRender
import com.yuno.sdk.payments.render.YunoPaymentFragmentController
import com.yuno.sdk.payments.render.YunoPaymentRenderListener
import com.yuno.payments.features.payment.models.OneTimeTokenModel
import com.yuno.presentation.core.components.PaymentSelected

class CheckoutActivity : ComponentActivity(), YunoPaymentRenderListener {

    private var controller: YunoPaymentFragmentController? = null

    fun pay(paymentSelected: PaymentSelected) {
        controller = startPaymentRender(
            checkoutSession = "session-from-backend",
            countryCode = "CO",
            submitButton = false,
            showPaymentStatus = false,
            coroutineScope = lifecycleScope,
            paymentSelected = paymentSelected,
            controller = this,
        )
    }

    override fun showView(fragment: Fragment) {
        // Embed in your layout
        supportFragmentManager.beginTransaction()
            .replace(R.id.yuno_form_container, fragment)
            .commit()
    }

    override fun loadingListener(isLoading: Boolean) { /* show your own loader */ }

    override fun returnStatus(resultCode: Int, paymentStatus: String, paymentSubStatus: String?) {
        // resultCode + paymentStatus
    }

    override fun returnOneTimeToken(oneTimeToken: String, additionalData: OneTimeTokenModel?) {
        // (only fires in the headless-render variant)
    }

    fun onPayButton() {
        controller?.submitForm()
    }

    // Called after the merchant's backend returns from 3DS / redirect
    fun onContinuePayment() {
        controller?.continuePayment()
    }
}
```

```kotlin After. showView override
import androidx.fragment.app.Fragment
import com.yuno.payments.sdk.api.Transaction
import com.yuno.payments.sdk.api.TransactionConfig
import com.yuno.payments.sdk.api.TransactionController
import com.yuno.payments.sdk.api.models.TransactionProcess
import com.yuno.payments.sdk.api.models.TransactionViewStep
import com.yuno.payments.sdk.api.models.PaymentMethodSelected
import com.yuno.payments.sdk.api.models.TransactionStatus

class CheckoutActivity : ComponentActivity(), TransactionController {

    private var process: TransactionProcess? = null

    fun pay(paymentSelected: PaymentMethodSelected) {
        val config = TransactionConfig(
            checkoutSession = "session-from-backend",
            countryCode = "CO",
            controller = this,
        )

        Transaction(config = config)
            .start(activity = this, paymentSelected = paymentSelected)
    }

    // 1. Embed the delivered fragment (called once per step: FORM, then ACTION for 3DS if applicable)
    override fun showView(view: Fragment, process: TransactionProcess, step: TransactionViewStep) {
        this.process = process
        supportFragmentManager.beginTransaction()
            .replace(R.id.yuno_form_container, view)
            .commit()
    }

    // 2. Override showLoading if you want to render your own loader
    override fun showLoading(isLoading: Boolean) { /* show your own loader */ }

    // 3. Final status arrives through onStatus
    override fun onStatus(status: TransactionStatus) {
        // status.status: "SUCCEEDED" / "REJECTED" / ...
    }

    fun onPayButton() {
        process?.onSubmit()
    }
}
```

</CodeGroup>

## O que muda {#what-changes}

Agrupado na ordem em que você edita o código. **Renomeado**: mesma função, novo nome. **Movido**: mesmo valor, novo dono. **Removido**: nada a chamar. A última coluna é a única coisa que você precisa fazer além da renomeação.

### Inicialização e configuração {#initialization-and-config}

| Render | Unificada | Mudança | O que fazer |
|---|---|---|---|
| `import com.yuno.sdk.*` | `import com.yuno.payments.sdk.api.*` | Renomeado | |
| Argumentos `checkoutSession` e `countryCode` de `startPaymentRender` | Os mesmos campos em `TransactionConfig` | Movido | Os argumentos da chamada viram campos da configuração. |
| Argumento `submitButton` de `startPaymentRender` | *(removido)* | Removido | Exclua-o: na API unificada, o botão de envio fica totalmente sob a sua responsabilidade. O SDK nunca renderiza um quando `showView` é sobrescrito; renderize-o no seu layout e chame `process.onSubmit()` quando for tocado (veja Views). |
| Argumento `showPaymentStatus` de `startPaymentRender` | `TransactionConfig.showStatusScreen` | Movido | Mesma função. |
| Argumento `coroutineScope` de `startPaymentRender` | *(removido)* | Removido | Exclua-o: o SDK gerencia o próprio escopo. |

### Controller {#controller}

| Render | Unificada | Mudança | O que fazer |
|---|---|---|---|
| `YunoPaymentRenderListener` | `TransactionController` | Renomeado | Implemente a mesma classe e passe-a como `TransactionConfig.controller` (era o argumento `controller` de `startPaymentRender`). O SDK não a retém: mantenha-a viva durante toda a transação. |
| `returnStatus(resultCode, paymentStatus, paymentSubStatus)` | `onStatus(status: TransactionStatus)` | Renomeado | Continua sendo o único callback de resultado, uma vez por transação, também quando o SDK mostra a tela de resultado. `resultCode` (os ints `PAYMENT_RESULT_*`) foi descartado: use `status.status` para ramificar a lógica. A string de status agora vem dentro de um objeto `TransactionStatus` cujos `status` e `substatus` vêm do backend, do jeito que o backend os retorna. As strings legadas `REJECT`, `FAIL` e `PROCESSING` não são mais emitidas: trate `DECLINED`, `REJECTED`, `ERROR` e `PENDING` em vez delas. `CANCELED_BY_USER` agora é `USER_CANCEL`; o próprio SDK só emite `INTERNAL_ERROR` e `USER_CANCEL`. Veja [`Status`](/pt-br/docs/yuno-sdk/reference/objects-you-receive#status). |
| `returnOneTimeToken(oneTimeToken, additionalData)` | `createPayment(token: Map<String, Any>)` | Renomeado | Opcional. Ele só era disparado na variante headless-render, então só é relevante para o caminho headless não seamless. Se você o usava, sobrescreva `createPayment`: `token` é o token de uso único completo como mapa. Crie o pagamento e retorne. Se o handler lançar um erro, o fluxo para e `onStatus` não é chamado, então mostre o erro você mesmo. Veja [`createPayment`](/pt-br/docs/yuno-sdk/controllers/create-payment) e [Migração do Headless](/pt-br/docs/yuno-sdk/migration/android/payment/headless). |
| `loadingListener(isLoading)` | `showLoading(isLoading)` | Renomeado | Mesma semântica. O Render é o modo legado em que o callback do loader de fato era invocado, então as integrações Render existentes quase certamente precisam migrar isso. Depois de sobrescrito, o SDK oculta o próprio loader e informa o estado a você. Veja [`showLoading`](/pt-br/docs/yuno-sdk/controllers/show-loading). |

### Views {#views}

| Render | Unificada | Mudança | O que fazer |
|---|---|---|---|
| `YunoPaymentRenderListener.showView(fragment)` | `showView(view, process, step)` | Renomeado | Push, não pull: você não chama mais nada para buscar o fragment, o SDK o entrega ao seu handler quando estiver pronto. `process` substitui o `YunoPaymentFragmentController`. `showView` pode ser chamado mais de uma vez por transação, e `step` informa qual etapa você recebeu: `FORM` para o formulário de captura de dados, `ACTION` para um desafio 3DS ou um redirecionamento externo. Decida como incorporar cada um no seu layout. Veja [`showView`](/pt-br/docs/yuno-sdk/controllers/show-view). |
| `controller.submitForm()` | `process.onSubmit()` | Renomeado | Mesma função. Chame-o no `TransactionProcess` que você recebe em `showView`. |
| `controller.continuePayment()` | *(removido)* | Removido | Exclua a chamada. O 3DS é tratado pelo SDK: quando um desafio 3DS ou um redirecionamento é necessário, ele mesmo aciona um segundo `showView(view, process, step = ACTION)`, e você pode continuar incorporando-o no seu layout. Você não precisa chamar nada. |

### Pontos de entrada {#entry-points}

| Render | Unificada | Mudança | O que fazer |
|---|---|---|---|
| `startPaymentRender(checkoutSession, countryCode, …, paymentSelected, controller)` retornando `YunoPaymentFragmentController` | `Transaction(config).start(activity, paymentSelected)` | Renomeado | Monte a configuração e depois chame `start`: a `Transaction` é o único ponto de entrada e a seleção vai para `start`. Sobrescreva `showView` para manter o formulário dentro do seu layout (veja Views). |
| `PaymentSelected` | `PaymentMethodSelected` | Renomeado | Mesma função: o valor que você passa para `start`. |
