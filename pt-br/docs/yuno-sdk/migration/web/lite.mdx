---
title: "Modo Lite"
description: "Migre integrações Lite na Web (yuno.startCheckout + yuno.mountCheckoutLite) para a API unificada de Transaction."
---

O modo Lite pré-selecionava o meio de pagamento no lado do lojista e depois passava o controle ao SDK para renderizar o formulário desse meio, tokenizar, criar o pagamento, tratar o 3DS e informar o resultado. Na API unificada, esse é o **comportamento padrão** de `transaction.start({ paymentMethod })`. Não é preciso sobrescrever nenhum controller além de `onStatus`.

## Antes de começar {#before-you-start}

- Carregue o bundle do SDK unificado em vez do legado e inicialize-o como mostra a comparação lado a lado: `window.Yuno.initialize(...)` vira `SdkPayments.initialize(...)`. Sua chave de API pública e as sessões de checkout que seu backend cria não mudam ([Antes de começar](/pt-br/docs/yuno-sdk/get-started#before-you-begin)).
- Decida quem cria o pagamento. O `workflow` da sessão de checkout precisa corresponder a essa decisão:

| Quem cria o pagamento | No Lite você tinha | Na API unificada | `workflow` da sessão |
|---|---|---|---|
| Seu backend | `yunoCreatePayment` implementado | Sobrescreva `createPayment` | Padrão (`SDK_CHECKOUT`) |
| O SDK | Sem `yunoCreatePayment` | Sem sobrescrita | `SDK_SEAMLESS` |

<Warning>
Uma sessão com o workflow padrão e sem sobrescrita de `createPayment` termina em `INTERNAL_ERROR`: o backend rejeita a criação do pagamento pelo SDK. Veja [`createPayment`](/pt-br/docs/yuno-sdk/controllers/create-payment).
</Warning>

## Lado a lado {#side-by-side}

<CodeGroup>

```typescript Before. Lite mode
// 1. Initialize once at page startup
const yuno = await window.Yuno.initialize('your-public-api-key')

// 2. Configure the checkout
await yuno.startCheckout({
    checkoutSession: 'session-from-backend',
    elementSelector: '#root',
    countryCode: 'CO',
    language: 'en',
    renderMode: { type: 'modal' },
    yunoPaymentResult: (status) => {
        console.log('Final status:', status)
    },
    yunoError: (error) => {
        console.log('Error', error)
    },
})

// 3. Mount Lite for the pre-selected payment method
await yuno.mountCheckoutLite({
    paymentMethodType: 'PIX',
    vaultedToken: null,
})
```

```typescript After. Unified Transaction
// 1. Initialize once at page startup
const sdkPayments = await SdkPayments.initialize('your-public-api-key')

// 2. Build the transaction and start with the pre-selected method
const transaction = sdkPayments.transaction({
    checkoutSession: 'session-from-backend',
    countryCode: 'CO',
    language: 'en',
    elementSelector: '#root',
    onStatus: (result) => {
        console.log('Final status:', result.status)
    },
})

await transaction.start({
    paymentMethod: { type: 'PIX' },
})
```

</CodeGroup>

## O que muda {#what-changes}

Agrupado na ordem em que você edita o código. **Renomeado**: mesma função, novo nome. **Movido**: mesmo valor, novo dono. **Removido**: nada a chamar. A última coluna é a única coisa que você precisa fazer além da renomeação.

### Inicialização e configuração {#initialization-and-config}

| Lite | Unificado | Mudança | O que fazer |
|---|---|---|---|
| `window.Yuno.initialize(publicApiKey)` | `SdkPayments.initialize(publicApiKey)` | Renomeado | O global é `window.SdkPayments`. Como antes, use `await`: ele resolve para a instância de `SdkPayments` a partir da qual você cria transações. |
| `checkoutSession`, `countryCode`, `language` na configuração de `startCheckout` | Os mesmos campos na configuração da transação | Movido | Mesmos campos, uma única factory: `sdkPayments.transaction({ checkoutSession, countryCode, language, … })`. |
| `elementSelector` na configuração de `startCheckout` | `elementSelector` na configuração da transação | Movido | Obrigatório para um formulário de pagamento. `start({ paymentMethod })` renderiza o formulário dentro desse elemento e lança um erro sem ele. Aceita um seletor CSS ou um `HTMLElement`. Fluxos headless o ignoram. As visualizações de carteira e de lista recebem o próprio `elementSelector` em `.mount()` (veja [`getPaymentMethodsViews`](/pt-br/docs/yuno-sdk/features/payment-methods-list)). |
| `renderMode: { type: 'modal' \| 'element', elementSelector }` | `elementSelector` na configuração da transação | Movido | O modo modal não existe mais. O formulário é renderizado dentro do elemento que você passa na configuração da transação. |
| `card: CardConfig` | `card: CardConfig` na configuração da transação | Movido | Mesmo formato. |
| `showPayButton` na configuração de `startCheckout` | `showPayButton` na configuração da transação | Movido | Mesmo significado. Só em fluxos de pagamento. |

### Callbacks {#callbacks}

| Lite | Unificado | Mudança | O que fazer |
|---|---|---|---|
| `yunoPaymentResult(status, subStatus?)` | `onStatus(result)` | Renomeado | Continua sendo o único callback de resultado, agora um campo na configuração da transação. Ele recebe um objeto `TransactionStatus` (`status`, `substatus`, `message`) em vez de dois argumentos posicionais: `status` não é mais a union do Lite. `result.status` traz o status do pagamento como a API o informa (`READY_TO_PAY`, `CREATED`, `SUCCEEDED`, `REFUNDED`, `REJECTED`, `CANCELED`, `ERROR`, `DECLINED`, `PENDING`, `EXPIRED`, `VERIFIED`) mais dois valores do SDK: `INTERNAL_ERROR` (um erro do SDK ou do backend, com detalhes em `result.message`) e `USER_CANCEL` (você desmontou antes de um resultado). Mapeie seus ramos `SUCCEEDED`, `REJECT`, `FAIL`, `PROCESSING` e `READY` para esses valores. `subStatus` vira `result.substatus`. Veja [`Status`](/pt-br/docs/yuno-sdk/reference/objects-you-receive#status). |
| `yunoCreatePayment(ott, info)` | `createPayment(token) => Promise<void>` | Renomeado | Opcional. Baseado em Promise, com um único argumento: `token` é o `OneTimeToken` mais `checkout_session`, a sessão à qual o token pertence (ela muda após uma recusa que permite nova tentativa). Crie o pagamento com `token.token` e `token.checkout_session` e depois resolva: resolver é o que antes era `continuePayment()`, e o SDK então orquestra o 3DS e a consulta do status. Veja [`createPayment`](/pt-br/docs/yuno-sdk/controllers/create-payment). |
| `yunoError(message, data?)` | *(removido)* | Removido | Todos os resultados finais passam por `onStatus` (um `TransactionStatus` com `message` definido) ou por uma Promise de `start()` rejeitada. |
| `onLoading({ isLoading, type })` | `showLoading(isLoading)` | Renomeado | Opcional. Remove o campo obsoleto `type`. Veja [`showLoading`](/pt-br/docs/yuno-sdk/controllers/show-loading). |

### Pontos de entrada {#entry-points}

| Lite | Unificado | Mudança | O que fazer |
|---|---|---|---|
| `yuno.startCheckout(config)` | `sdkPayments.transaction(config)` | Renomeado | Uma única factory: monte a transação com a configuração (campos e callbacks acima) e depois chame `start`. |
| `yuno.mountCheckoutLite({ paymentMethodType, vaultedToken })` | `transaction.start({ paymentMethod: { type: paymentMethodType, vaultedToken } })` | Renomeado | A pré-seleção do Lite vira o argumento `paymentMethod` de `start()`. |
| `yuno.submitOneTimeTokenForm()` | `transaction.submit()` | Renomeado | Envia o formulário que `start()` montou, a partir do seu próprio botão. Use com `showPayButton: false`. Veja [Web: enviar a partir do seu próprio botão](/pt-br/docs/yuno-sdk/controllers/show-view#web-submit-from-your-own-button). |
| `yuno.continuePayment()` | *(removido)* | Removido | Exclua a chamada. O Lite exigia chamá-la dentro de `yunoCreatePayment` para avançar o fluxo; agora o SDK orquestra o 3DS e a consulta do status automaticamente quando `createPayment` é resolvido. |
