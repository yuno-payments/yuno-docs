Registre o callback opcional `onCardInfoChanged` para receber a bandeira, o tipo, a categoria, o emissor e o país do cartão enquanto o comprador digita o número do cartão no formulário de cartão. Você recebe esses detalhes antes de o comprador enviar o formulário, então pode adaptar seu checkout em tempo real: mostrar a bandeira do cartão ou o banco emissor no resumo do pedido, explicar uma promoção que vale apenas para cartões de crédito ou adaptar uma mensagem ao país do banco emissor.

O callback é informativo e opcional: se você não registrá-lo, o comportamento do SDK não muda. O SDK já consulta os detalhes do cartão a partir do sexto dígito para mostrar a bandeira e carregar as parcelas, e o callback entrega a você o resultado dessa mesma consulta. Ele não faz nenhuma chamada de rede extra e nunca inclui o número completo do cartão, o código de segurança, a data de validade ou o nome do titular do cartão.

| Plataforma | Disponível a partir de | Onde registrar |
| -------- | -------------- | ----------------- |
| iOS      | SDK `2.30.0`   | `onCardInfoChanged(_:)` em `YunoPaymentDelegate` ou `YunoEnrollmentDelegate`. Para o Seamless, `SeamlessParams.onCardInfoChanged` |
| Android  | SDK `2.29.0`   | `setOnCardInfoChanged { }`, chamado antes de você iniciar o checkout ou o cadastro |

O callback é disparado em todo formulário de cartão que o SDK mostra para um cartão novo, em pagamentos e em cadastros. Ele não é chamado para cartões salvos (cadastrados), porque o comprador não digita um número, nem em integrações headless, porque nelas o SDK não mostra nenhum formulário de cartão.

## O que você recebe {#what-you-receive}

Um objeto de informações do cartão, ou `null` (`nil` no iOS), conforme descrito em [Quando ele é chamado](#when-it-is-called).

| Propriedade      | Chave            | Descrição                                                                                             |
| ------------- | -------------- | ------------------------------------------------------------------------------------------------------- |
| `iin`         | `iin`          | Primeiros dígitos do número do cartão, entre 6 e 8. Nunca o número completo.                                |
| `brand`       | `brand`        | Bandeira do cartão, por exemplo `VISA` ou `MASTERCARD`.                                                         |
| `scheme`      | `scheme`       | Esquema do cartão.                                                                                            |
| `type`        | `type`         | Tipo do cartão, normalmente `CREDIT` ou `DEBIT`.                                                               |
| `category`    | `category`     | Categoria ou nível do cartão, por exemplo `GOLD` ou `PREPAID`. Cartões pré-pagos são sinalizados aqui, não em `type`. |
| `issuerName`  | `issuer_name`  | Nome do banco emissor.                                                                               |
| `issuerCode`  | `issuer_code`  | Código do banco emissor.                                                                               |
| `countryCode` | `country_code` | Código ISO do país do banco emissor, por exemplo `BR`.                                                 |
| `countryName` | `country_name` | Nome do país do banco emissor.                                                                       |

* Os valores são repassados exatamente como a consulta do cartão os retorna. O SDK não os traduz nem os normaliza.
* Um valor que a consulta não retorna é `null` (`nil` no iOS). Alguns campos, como `issuerCode`, costumam vir vazios, então não os torne obrigatórios na sua lógica.
* No iOS, `iin` está sempre presente. Todos os outros campos são opcionais nas duas plataformas.
* O tamanho de `iin` varia entre 6 e 8 dígitos. Não dependa dele.
* Cada valor também está disponível por chave: `rawData` no iOS e `toMap()` no Android sempre retornam as nove chaves acima, com os mesmos nomes nas duas plataformas. No iOS, um valor ausente em `rawData` é `NSNull`.

## Quando ele é chamado {#when-it-is-called}

* Depois que a consulta do cartão responde, assim que o comprador tiver digitado pelo menos 6 dígitos.
* De novo, apenas quando o resultado muda. Digitar mais dígitos do mesmo cartão não o chama de novo, a menos que a consulta retorne detalhes diferentes. No iOS, uma nova chamada também pode chegar quando a consulta encontra um prefixo mais longo do mesmo cartão, com apenas o `iin` alterado.
* Com `null` (`nil` no iOS) quando um cartão que você já recebeu deixa de valer: o número cai para menos de 6 dígitos, o campo é apagado ou a consulta falha. A primeira chamada nunca é `null`.
* Na thread principal, então você pode atualizar sua UI diretamente.

Se o comprador continuar digitando ou editar o número enquanto uma consulta está em andamento, as respostas desatualizadas são descartadas, então você nunca recebe os detalhes de um número que o comprador já alterou.

Nada é enviado quando o formulário de cartão fecha, quando o comprador paga ou quando o comprador escolhe outro meio de pagamento: o último valor que você recebeu continua valendo. Se a sua UI precisar redefini-lo nesses casos, faça isso do seu lado.

Cada formulário de cartão começa do zero. Se o comprador fechar o formulário e abri-lo de novo, o primeiro resultado no novo formulário é entregue mesmo que seja o mesmo cartão de antes.

| O que o comprador faz                            | O que você recebe                                           |
| ------------------------------------------------ | ---------------------------------------------------------- |
| Digita os 5 primeiros dígitos                         | Nada.                                                   |
| Digita o 6º dígito                              | Os detalhes do cartão, assim que a consulta responde.           |
| Continua digitando o mesmo cartão                       | Nada, a menos que a consulta retorne detalhes diferentes.      |
| Apaga dígitos até restarem menos de 6         | `null` (`nil` no iOS).                                     |
| Digita o número de outro cartão             | Os detalhes do novo cartão.                               |
| A consulta falha, por exemplo sem conexão | `null` (`nil` no iOS), se você tiver recebido um cartão antes.  |
| Paga, fecha o formulário ou escolhe outro meio    | Nada mais. O último valor continua valendo.                       |

## Implementação {#implementation}

<Tabs>
<Tab title="iOS">

Implemente o método opcional `onCardInfoChanged(_:)` no delegate que você passa para o SDK: `YunoPaymentDelegate` para pagamentos (Full, Lite e Render) e `YunoEnrollmentDelegate` para cadastros. O método é o mesmo nos dois.

```swift
class CheckoutViewController: UIViewController, YunoPaymentDelegate {

    // ... required YunoPaymentDelegate implementation ...

    func onCardInfoChanged(_ cardInfo: YunoCardInfo?) {
        guard let cardInfo else {
            // The card you received no longer applies
            orderSummary.clearCardDetails()
            return
        }
        orderSummary.showCardDetails(
            brand: cardInfo.brand,
            type: cardInfo.type,
            issuer: cardInfo.issuerName,
            country: cardInfo.countryCode
        )
    }
}
```

O método recebe um payload `YunoCardInfo?`, também disponível em Objective-C:

```swift
@objc public final class YunoCardInfo: NSObject {
    @objc public let iin: String
    @objc public let brand: String?
    @objc public let scheme: String?
    @objc public let type: String?
    @objc public let category: String?
    @objc public let issuerName: String?
    @objc public let issuerCode: String?
    @objc public let countryCode: String?
    @objc public let countryName: String?
    @objc public let rawData: [String: Any]
}
```

Para ler os valores por chave, use `rawData`:

```swift
func onCardInfoChanged(_ cardInfo: YunoCardInfo?) {
    guard let values = cardInfo?.rawData else { return }
    let category = values["category"] as? String
    if category == "PREPAID" {
        orderSummary.showPrepaidNotice()
    }
}
```

Para o Seamless, defina `SeamlessParams.onCardInfoChanged` em vez disso, porque o Seamless não recebe um delegate. Defina a closure antes de chamar `startPaymentSeamlessLite`: ela é lida uma única vez, quando o pagamento começa.

```swift
let params = SeamlessParams(
    checkoutSession: checkoutSession,
    countryCode: "CO",
    language: "en",
    viewController: self
)
params.onCardInfoChanged = { [weak self] cardInfo in
    self?.orderSummary.update(with: cardInfo)
}
let result = await Yuno.startPaymentSeamlessLite(with: params, paymentSelected: paymentSelected)
```

Em Objective-C:

```objectivec
- (void)onCardInfoChanged:(YunoCardInfo * _Nullable)cardInfo {
    if (cardInfo == nil) {
        [self.orderSummary clearCardDetails];
        return;
    }
    [self.orderSummary showBrand:cardInfo.brand type:cardInfo.type];
}
```

<Tab title="Android">

Chame `setOnCardInfoChanged` uma vez, antes de iniciar o checkout, o pagamento ou o cadastro. Um único registro cobre todos os formulários de cartão (`startPayment`, `startPaymentLite`, `startPaymentSeamlessLite`, `startPaymentRender`, `startEnrollment` e `startEnrollmentRender`) até você substituí-lo.

```kotlin
import com.yuno.sdk.payments.CardInfo
import com.yuno.sdk.payments.setOnCardInfoChanged

class CheckoutActivity : AppCompatActivity() {

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setOnCardInfoChanged { cardInfo -> renderCardDetails(cardInfo) }
        startCheckout(
            checkoutSession = "checkout_session",
            countryCode = "country_code_iso",
            callbackPaymentState = { state, subState, message -> /* ... */ },
        )
    }

    override fun onDestroy() {
        setOnCardInfoChanged(null)
        super.onDestroy()
    }

    private fun renderCardDetails(cardInfo: CardInfo?) {
        if (cardInfo == null) {
            orderSummary.clearCardDetails()
            return
        }
        orderSummary.showCardDetails(cardInfo.brand, cardInfo.type, cardInfo.issuerName, cardInfo.countryCode)
    }
}
```

Chame `setOnCardInfoChanged(null)` quando não precisar mais dele, por exemplo em `onDestroy`. O SDK mantém o callback até você substituí-lo ou passar `null`, então, caso contrário, uma lambda que captura uma `Activity` a manteria na memória.

Se você registrar o callback depois que o formulário de cartão estiver aberto, receberá a próxima mudança, não o cartão que já está na tela.

Para ler os valores por chave, use `toMap()`:

```kotlin
setOnCardInfoChanged { cardInfo ->
    val values: Map<String, String?> = cardInfo?.toMap() ?: return@setOnCardInfoChanged
    if (values["category"] == "PREPAID") {
        orderSummary.showPrepaidNotice()
    }
}
```

Em Java:

```java
import com.yuno.sdk.payments.PaymentsFlowKt;
import kotlin.Unit;

PaymentsFlowKt.setOnCardInfoChanged(cardInfo -> {
    if (cardInfo == null) {
        orderSummary.clearCardDetails();
    } else {
        orderSummary.showCardDetails(cardInfo.getBrand(), cardInfo.getType());
    }
    return Unit.INSTANCE;
});
```

Uma exceção lançada dentro do seu callback é capturada e registrada pelo SDK, então ela não pode quebrar o formulário de cartão. Trate seus próprios erros mesmo assim, porque o SDK não repete a chamada.

## Boas práticas {#best-practices}

* Mantenha o handler leve. Ele roda na thread principal enquanto o comprador digita, então tire da thread principal qualquer trabalho lento, como uma chamada ao seu backend.
* Trate `null` (`nil` no iOS): limpe ou oculte o que você mostrou para o cartão anterior.
* Trate cada chamada como o estado atual do formulário, não como um valor final. O comprador ainda pode alterar o número antes de pagar.
* Não bloqueie nem atrase o pagamento com base nesses valores. O SDK valida o cartão por conta própria.

## Testes {#testing}

1. No sandbox, abra um formulário de cartão no seu app com o callback registrado.
2. Digite o número de um cartão de teste. Depois do sexto dígito, você recebe os detalhes do cartão.
3. Apague dígitos até restarem menos de 6. Você recebe `null` (`nil` no iOS).
4. Digite o número de um cartão de outra bandeira. Você recebe os novos detalhes.
5. Pague com um cartão salvo. O callback não é chamado.

Os valores vêm da consulta de cartão do ambiente que você usa, então cartões de teste no sandbox podem retornar dados genéricos do emissor.
