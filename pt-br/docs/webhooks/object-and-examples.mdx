## Atributos do webhook {#webhook-attributes}

Os atributos JSON dos webhooks da Yuno estão listados abaixo. Consulte [Eventos e gatilhos](/pt-br/docs/webhooks/events) para ver o campo de gatilho que seleciona cada evento.

<ParamField body="account_id" type="string">
   O identificador único da conta na Yuno (MAX 64, MIN 36).
</ParamField>

<ParamField body="type" type="string">
  Especifica o tipo de notificação.
</ParamField>

<ParamField body="type_event" type="string">
  Especifica o tipo de notificação do evento.
</ParamField>

<ParamField body="version" type="string">
  Especifica a versão do webhook enviado. Atualmente, 2.
</ParamField>

<ParamField body="retry" type="string">
  Especifica o número de novas tentativas dessa notificação.
</ParamField>

<ParamField body="data" type="object">
  Especifica o [pagamento](/reference/payments/the-payment-object) (para o tipo pagamento) ou o [objeto do meio de pagamento](/pt-br/reference/payment-methods-direct-workflow/the-payment-method-object-api) (para cadastro e outros objetos).

  <Expandable title="propriedades">
    <ParamField body="idempotency_key" type="string">
      Identificador usado para ignorar entregas duplicadas. Ele se mantém estável em todas as novas tentativas do mesmo evento. A localização depende do evento: os eventos de pagamento comuns (incluindo reembolso e chargeback) o trazem em `data.payment.idempotency_key`, `payment.split_update` o traz em `data.split_update.idempotency_key` e os eventos de assinatura o trazem em `data.idempotency_key`. Nos eventos `subscription.*`, ele identifica a assinatura e não o evento, então elimine as duplicatas desses eventos usando `type_event` mais essa chave. Consulte [Eliminação de duplicatas](/docs/webhooks#de-duplication) para ver os detalhes de cobertura.
    </ParamField>
  </Expandable>
</ParamField>

<ParamField body="x-hmac-signature" type="string">
  Opcional. A assinatura HMAC-SHA256 enviada no cabeçalho HTTP para a verificação do webhook quando a autenticação HMAC está ativada.
</ParamField>

## Webhooks de atualização de split {#split-update-webhooks}

Estes exemplos resumidos mostram apenas os campos necessários para interpretar `payment.split_update`; os campos normais do pagamento também são incluídos. Este evento exige uma assinatura explícita e está pendente de disponibilidade no catálogo de produção.

Na v2, o envelope identifica `type_event: "payment.split_update"`, e o bloco da operação é `data.split_update`:

```json
{
  "type": "payment",
  "type_event": "payment.split_update",
  "version": 2,
  "retry": 0,
  "data": {
    "split_update": {
      "idempotency_key": "4a518553-a6e7-4717-a415-06084ea85c99",
      "updated_at": "2026-09-22T04:20:00Z"
    },
    "payment": {
      "transactions": {
        "split_marketplace": []
      }
    }
  }
}
```

Este exemplo limpa o split, então o `split_marketplace` da operação é `[]`. Uma substituição aplicada traz, em vez disso, as entradas de split dessa operação. `transactions` é um único objeto, não um array.

A v1 legada envia o corpo do pagamento sem o envelope da v2 nem `type_event`. Identifique este evento pelo bloco `split_update` ao lado de `payment`:

```json
{
  "split_update": {
    "idempotency_key": "4a518553-a6e7-4717-a415-06084ea85c99",
    "updated_at": "2026-09-22T04:20:00Z"
  },
  "payment": {
    "transactions": {
      "split_marketplace": []
    }
  }
}
```

| Campo | Significado |
| --- | --- |
| `split_update.idempotency_key` | A chave da requisição original de atualização de split. Use-a para distinguir operações e eliminar entregas duplicadas, no escopo da conta e do tipo de evento. |
| `split_update.updated_at` | O horário de conclusão registrado da operação, preservado em resoluções repetidas e em notificações atrasadas. |
| `payment.transactions.split_marketplace` | O snapshot do split da operação selecionada, incluindo `[]` para uma limpeza. |

Se `transactions_history` estiver ativado, a entrada dele para a transação afetada traz o mesmo split da operação. O evento não ativa o histórico nem substitui o `payment.split_marketplace` no nível do pagamento; não use esse campo do nível do pagamento como snapshot desta operação. Os outros campos refletem o pagamento lido quando a notificação é preparada e podem incluir alterações posteriores. Use `GET /v1/payments/{payment_id}` para obter o estado mais recente do pagamento.

Não há garantia de que o snapshot da operação seja serializado de forma idêntica a uma leitura posterior do pagamento. A escala numérica pode ser diferente (por exemplo, `5` versus `5.0`), e um objeto de responsabilidade que contém apenas `chargebacks` pode ser representado de outra forma pelo mapeamento do pagamento ativo. Compare os valores e o significado deles em vez de exigir igualdade de JSON byte a byte. Essas diferenças de representação não identificam uma nova operação de split.

Apenas este evento adiciona `split_update`; os payloads de compra e de reembolso não recebem o bloco. Consulte [Notificações de atualização de split](/docs/webhooks#split-update-notifications) para ver o comportamento de assinatura, emissão, ordenação e entrega.

## Pagamento {#payment}

### Webhook de pagamento V2 {#payment-webhook-v2}

Exemplo de payload:

<Info>
  Os payloads de webhook de eventos correspondentes a um meio de pagamento de transferência bancária incluem `payment.payment_method.payment_method_detail.bank_transfer.bank_id`. O campo reflete o `bank_id` enviado na requisição original do pagamento e é omitido quando nenhum banco foi selecionado.
</Info>

<Info>
  Quando o pagamento traz uma seleção de frete (por exemplo, escolhida dentro de um widget de carteira com o [frete do Fast Checkout](/pt-br/docs/payment-features/fast-checkout-shipping)), o payload inclui um nó `payment.shipping` no nível superior (com o mesmo formato do [objeto de pagamento](/reference/payments/the-payment-object)) nas versões V1 e V2, e `payment.customer_payer.shipping_address` é preenchido a partir dele quando o pagador não tinha um. A chave `shipping` é omitida quando o pagamento não tem seleção.
</Info>

<Info>
  Cada transação inclui `connection_data`, que identifica a conexão do provedor que a processou. Use `connection_data.id` como identificador estável para atribuir transações a uma conexão específica quando você opera várias conexões com o mesmo provedor. `connection_data.name` é o nome de exibição configurado no Dashboard da Yuno e pode ser `null` em alguns eventos, como transações de acompanhamento.
</Info>

<Info>
  O campo `transactions` tem um significado diferente em cada superfície. Nos payloads de webhook, `data.payment.transactions` é um **único objeto** (a transação que disparou o evento), e `transactions_history` traz a lista completa das transações do pagamento quando ele está ativado para o pagamento (veja a nota abaixo). Nos endpoints de consulta de pagamento (`GET /payments/{payment_id}` e `GET /payments?merchant_order_id=`), `transactions` é um **array** que contém todas as transações do pagamento.
</Info>

<Info>
  `transactions_history` é **opcional (opt-in)**: ele só é preenchido quando o pagamento foi criado com `response_additional_data.transactions_history: true` na requisição de [Criar pagamento](/reference/payments/create-payment). Caso contrário, os webhooks o entregam como um array vazio `[]`, o padrão, que mantém os payloads pequenos. Isso importa para pagamentos que o seu roteamento tenta novamente em outros provedores: sem a flag, o webhook final mostra apenas a última transação, e as tentativas anteriores só ficam visíveis via `GET /payments/{payment_id}`. Pagamentos criados por fluxos gerenciados pela Yuno que não definem a flag (por exemplo, renovações de assinatura) também entregam `[]`. Os eventos de chargeback sempre incluem o histórico completo.
</Info>

<Info>
  Nomenclatura de campos: a geolocalização do cliente é serializada como `geo_location` nos payloads de webhook e como `geolocation` nos endpoints de consulta de pagamento. Interprete cada superfície de acordo.
</Info>

<Info>
  `payment.amount.authorized` é o valor que o provedor aprovou, já descontada qualquer promoção da Yuno, como no [objeto de pagamento](/reference/payments/the-payment-object). Um pagamento com cartão enviado com `partial_approval: true` mantém o status de uma aprovação total após uma aprovação parcial, então ele está parcialmente aprovado quando `payment.amount.authorized` é menor que `payment.amount.value` menos `payment.discount_amount` (quando não há promoção, menor que `payment.amount.value`). O campo é omitido em pagamentos que não foram aprovados ou que foram criados antes de ele ser introduzido. As duas versões do webhook trazem o campo.
</Info>

### subscription.creation_failed {#subscriptioncreationfailed}

Enviado para pagamentos do [Stripe Billing](/pt-br/docs/payment-features/subscriptions/stripe-billing) quando um pagamento `SUCCEEDED` que traz `external_subscription` não conseguiu criar a assinatura no Stripe. O dinheiro foi capturado, e nenhuma assinatura do Stripe foi criada ou ativada. Enviado uma vez por falha. Não é enviado quando o pagamento já foi reembolsado ou parcialmente reembolsado. Assine com o valor `CREATION_FAILED` em `subscription_triggers`.

Diferente dos outros eventos de assinatura, `data` não traz um objeto de assinatura da Yuno, porque nenhum existe:

| Campo | Tipo | Descrição |
| :---- | :--- | :---------- |
| `payment_id` | string (UUID) | O pagamento da Yuno que foi capturado. |
| `external_subscription` | object | O objeto `external_subscription` exatamente como você o enviou no pagamento. |
| `dead_letter_kind` | string | Por que a assinatura não foi criada, por exemplo `incomplete_payload`, `tax_quote_expired`, `tax_not_calculated` ou `stripe_resource_missing`. Trate-o como aberto: novos valores podem ser adicionados. |
| `reason` | string | Uma descrição curta e legível de `dead_letter_kind`. Não faça parsing dela. |
| `occurred_at` | string (ISO 8601, UTC) | Quando a Yuno desistiu de criar a assinatura. |

Ainda não existe uma captura real deste evento. O exemplo abaixo foi montado a partir do contrato do evento; os identificadores são ilustrativos.
</Note>

### subscription.cycle_executed {#subscriptioncycleexecuted}

Enviado para assinaturas baseadas em plano quando um ciclo de `$0` é executado, seja um ciclo de teste ou um ciclo com desconto total. Esses ciclos não geram webhook `payment.purchase`, então este evento é o único comprovante deles. `reason` é `TRIAL` ou `FULL_DISCOUNT`, `phase` é a fase à qual o ciclo pertence, e `breakdown` traz o mesmo detalhamento por item de um ciclo pago, com total zero.

Em um ciclo com desconto de uma assinatura com uma [promoção](/pt-br/docs/payment-features/subscriptions/promotions) ativa, o evento também inclui um objeto `promotion` em `data`. Ele traz o `id` da promoção, o `discount_amount` descontado dessa cobrança e `cycles_remaining`, o número de ciclos com desconto que restam depois deste. Uma cobrança de preço cheio sem promoção não envia este evento. Um ciclo com desconto cobrado não traz `reason`. `reason` só é `FULL_DISCOUNT` quando a cobrança do ciclo é 0.

| Ciclo | Enviado? |
| :---- | :---- |
| Cobrança aprovada com desconto | Sim. Inclui o objeto `promotion` e é enviado depois que o ciclo é contabilizado. |
| Nova tentativa automática ou forçada, aprovada | Sim, uma vez por ciclo, com o objeto `promotion`. |
| Resultado tardio, aprovado | Sim, uma vez, quando o resultado chega. |
| Cobrança recusada | Não. |
| Ciclo de teste | Enviado apenas para assinaturas em um plano com fases, como hoje (reason `TRIAL`). Quando o ciclo de teste conta para uma promoção, o evento inclui o objeto da promoção com `discount_amount` 0. |
| Ciclo de $0 de uma fase de um plano com fases, sem promoção | Sim, com reason `TRIAL` ou `FULL_DISCOUNT`. Sem alterações. |
| Ciclo de 100% (`FULL_DISCOUNT`) | Sim, com reason `FULL_DISCOUNT`. O objeto `promotion` é incluído quando pode ser lido. |
| Cobrança de preço cheio sem promoção | Não. |

}

### Cobranças de renovação e falhas (sem `subscription.error`) {#renewal-charges-and-failures-no-subscriptionerror}

<Warning>
**Não existe webhook `subscription.error`**. A Yuno não emite um evento de assinatura quando uma cobrança de renovação falha. Os resultados das cobranças de renovação, tanto as recobranças bem-sucedidas quanto as tentativas com falha ou recusadas, são entregues como webhooks `payment.purchase` vinculados à assinatura, com o resultado nos campos `status`/`sub_status`. Assine `payment.purchase` para acompanhar os resultados das renovações. Ciclos de `$0`/teste não emitem webhook de pagamento; em assinaturas baseadas em plano, eles são informados como [`subscription.cycle_executed`](#subscription-cycle_executed).
</Warning>

<Note>
A **cobrança** da renovação em si é sempre sinalizada por um webhook `payment.purchase`, nunca por um webhook de assinatura. O array `payments` dentro do objeto de assinatura está sempre vazio nos payloads de webhook atualmente. `subscription.active` é enviado quando a assinatura fica ativa pela primeira vez (em `billing_cycles.current` = 2), não a cada renovação; ele só é enviado de novo quando uma assinatura se recupera de `PAST_DUE`.
</Note>

<Note>
Uma renovação com falha gera, sim, um webhook de assinatura em dois casos. Onde o status `PAST_DUE` está ativado para a conta, a primeira cobrança com falha de um ciclo move a assinatura para `PAST_DUE` e emite [`subscription.past_due`](#subscription-past_due). E, se a assinatura tiver `retries.cancel_on_exhausted_retries` definido como `true`, quando as novas tentativas desse ciclo terminam sem um pagamento bem-sucedido, a assinatura é cancelada e um único [`subscription.cancel`](#subscription-cancel) é emitido com `cancellation_source` definido como `RETRIES_EXHAUSTED`. Isso ainda não é um `subscription.error`: as tentativas individuais com falha continuam sendo webhooks `payment.purchase`. Apenas o cancelamento final é sinalizado na assinatura.
</Note>

## Transferências de split do marketplace {#marketplace-split-transfers}

As notificações de transferência avulsa incluem a `direction` salva no nível superior do corpo JSON entregue. As transferências existentes usam `PLATFORM_TO_RECIPIENT`. A disponibilidade de destinatário para plataforma segue o [endpoint de criação](/reference/transfers/create-standalone-transfer).

Os exemplos abaixo mostram campos selecionados do corpo entregue. Os títulos são os tipos de evento da assinatura; o corpo entregue é o próprio objeto de transferência, sem envelope e sem campo de tipo de evento. Identifique uma notificação de estorno pelo `status` (`REVERSED` ou `REVERSED_PARTIAL`) e por uma transação do tipo `SPLIT_TRANSFER_REVERSE`. `provider_data` descreve a conta do provedor que processou a transferência; o `raw_response` de cada transação traz a resposta bruta do provedor, serializada em JSON como string.

<Note>
Segundo a engenharia, o `type_event` sob o qual esses dois eventos são registrados internamente é `transfer.transfer`; o corpo do webhook entregue em si não traz envelope `type`/`type_event`, como indicado acima.
</Note>

### split_transfer_reverse.succeeded {#splittransferreversesucceeded}

A notificação identifica a transferência original, mantém a direção dela e inclui tanto a transação original quanto a de estorno. Neste exemplo de estorno parcial, `status` é `REVERSED_PARTIAL` e `amount` é o valor de estorno de USD 1. A transação de estorno aponta para a transação original por meio de `parent_transaction_code`. Esta notificação é diferente da resposta HTTP do estorno, que não inclui a direção. Ela é entregue com o `id` da transferência original; `description` e `merchant_reference` trazem os valores enviados na requisição de estorno.
