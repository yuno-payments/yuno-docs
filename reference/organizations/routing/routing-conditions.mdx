A condition matches against an attribute of the incoming payment.

```jsonc
{
  "condition_type": "<ENUM>",
  "conditional":    "<OPERATOR>",
  "values":         ["..."],

  // Required only on specific condition_types — see "Special cases" below
  "key":      "<string>",   // METADATA only
  "currency": "<ISO 4217>"  // AMOUNT only
}
```

Conditions inside the same `condition_sets[].conditions[]` are combined with **logical AND**. For OR semantics, split into multiple condition sets ordered by `sort_number`.

#### `condition_type` catalog

| `condition_type` | Matches against | Value shape | Applicable `conditional`s | Card-only? |
|---|---|---|---|---|
| `COUNTRY` | Transaction country — the top-level `country` field you submit in `POST /v1/payments` (never the card) | ISO 3166-1 alpha-2 (e.g. `"US"`, `"BR"`) | `EQUAL`, `NOT_EQUAL`, `ONE_OF`, `NOT_ONE_OF` | no |
| `CARD_ISSUER_COUNTRY` | Card-issuing bank's country, resolved by Yuno's BIN lookup at processing time | ISO 3166-1 alpha-2 | `EQUAL`, `NOT_EQUAL`, `ONE_OF`, `NOT_ONE_OF` | yes |
| `AMOUNT` | Transaction amount. Sent as `AMOUNT` with a sibling `currency` field; Yuno stores it internally as `CURRENCY_AND_AMOUNT` | Decimal as **string** (e.g. `"100.00"`); requires sibling `currency` | `EQUAL`, `NOT_EQUAL`, `GREATER_THAN`, `LESS_THAN`, `BETWEEN`, `NOT_BETWEEN` | no |
| `CARD_TYPE` | Card funding source | `CREDIT`, `DEBIT`, `PREPAID` | `EQUAL`, `NOT_EQUAL`, `ONE_OF`, `NOT_ONE_OF` | yes |
| `CARD_BRAND` | Card scheme, as Yuno resolves it from the BIN at processing time | The exact brand label Yuno resolved — see [`CARD_BRAND` values](#card-brand-values) below | `EQUAL`, `NOT_EQUAL`, `ONE_OF`, `NOT_ONE_OF` | yes |
| `CARD_BIN` | First 6–8 digits of the PAN | 6–8 digit numeric string | `EQUAL`, `NOT_EQUAL`, `ONE_OF`, `NOT_ONE_OF` | yes |
| `TRANSACTION_TYPE` | Payment intent type | `PURCHASE`, `AUTHORIZATION`, `RECURRING`, `MIT`, `CIT` | `EQUAL`, `NOT_EQUAL`, `ONE_OF`, `NOT_ONE_OF` | no |
| `METADATA` | `payment.metadata[<key>]` | Any string the merchant sets; requires sibling `key` | `EQUAL`, `NOT_EQUAL`, `ONE_OF`, `NOT_ONE_OF` | no |

<Warning>
`CURRENCY` and `INSTALLMENTS` are **not** valid standalone `condition_type` values. Sending either one rejects the whole routing with `400 INVALID_ROUTE_CONFIGURATION`. To filter by currency, use `AMOUNT` with the sibling `currency` field.
</Warning>

#### `conditional` operators

| Operator | Cardinality of `values[]` | Semantics |
|---|---|---|
| `EQUAL` | exactly 1 | `attribute == values[0]` |
| `NOT_EQUAL` | exactly 1 | `attribute != values[0]` |
| `ONE_OF` | ≥ 1 | `attribute ∈ values` |
| `NOT_ONE_OF` | ≥ 1 | `attribute ∉ values` |
| `GREATER_THAN` | exactly 1 | numeric `attribute > values[0]` |
| `LESS_THAN` | exactly 1 | numeric `attribute < values[0]` |
| `BETWEEN` | exactly 2 | inclusive on both ends |
| `NOT_BETWEEN` | exactly 2 | inverse of `BETWEEN` |

#### Special cases

- **`AMOUNT` requires `currency`.** Comparisons are FX-naive; only payments whose currency matches the rule's `currency` are evaluated.
- **`METADATA` requires `key`.** Compares `payment.metadata[key]`. If the key is absent on the payment, the condition does **not** match — absence is not equality.
- **Card-only condition types** (`CARD_ISSUER_COUNTRY`, `CARD_TYPE`, `CARD_BRAND`, `CARD_BIN`) are only valid when `payment_method = "CARD"`.
- **`COUNTRY` vs `CARD_ISSUER_COUNTRY`.** The two are sourced independently: `COUNTRY` matches the transaction country your backend submits in the payment request, while `CARD_ISSUER_COUNTRY` matches the issuer country Yuno's own BIN lookup derives from the card number. The same payment can be `COUNTRY = US` and `CARD_ISSUER_COUNTRY = GB` at once. The BIN lookup runs before a provider is selected, is identical in sandbox and production, and reflects real-world BIN-registry data — never the processor's view of the card.
- **Numeric values are submitted as strings** to match the `values: string[]` schema. Yuno parses them based on the `condition_type`.

#### `CARD_BRAND` values {#card-brand-values}

`CARD_BRAND` is matched as an **exact, case-insensitive string** against the brand Yuno resolved for the card. There is no fixed enum: the value you send must equal the resolved label, so a label that looks right but is not the one Yuno produces simply never matches, and the condition set is skipped without an error.

The brands below carry live card volume on Yuno. Use these spellings.

| Value | Also seen as | Notes |
|---|---|---|
| `VISA` | | |
| `MASTERCARD` | | |
| `AMERICAN_EXPRESS` | `AMEX`, `AMERICAN EXPRESS` | Use `AMERICAN_EXPRESS`. The other two exist on a small number of cards; see the warning below |
| `DINERS` | `DINERS_CLUB_INTERNATIONAL` | Use `DINERS` |
| `DISCOVER` | | |
| `JCB` | | |
| `CHINA_UNION_PAY` | | Not `UNIONPAY` |
| `MAESTRO` | | |
| `CARTES_BANCAIRES` | | Not `CB` |
| `ELO` | | Brazil |
| `HIPERCARD` | | Brazil |
| `AURA` | | Brazil |
| `CABAL` | | Argentina |
| `TARJETA_NARANJA` | | Argentina |
| `ARGENCARD` | | Argentina |
| `CARNET` | | Mexico |
| `CODENSA` | | Colombia |
| `TROY` | | Türkiye |
| `RUPAY` | | India |
| `NSPK_MIR` | | |
| `ALELO`, `EDENRED`, `PLUXEE`, `VR_VALE_REFEICAO` | `SODEXO` for Pluxee | Benefit and voucher cards, Brazil |
| `EBT`, `PRIVATE_LABEL`, `LOCAL_BRAND` | | Generic labels for cards with no specific scheme |

<Warning>
**Three spellings changed and one is a trap.**

Earlier versions of this page listed `AMEX`, `UNIONPAY` and `CB`. Only the first of those ever matches anything:

- `UNIONPAY` and `CB` match nothing at all. Use `CHINA_UNION_PAY` and `CARTES_BANCAIRES`.
- `AMEX` **does** match a very small number of cards, so a rule written with it is accepted, looks correct and quietly routes almost no American Express traffic. Use `AMERICAN_EXPRESS`, and add `AMEX` and `AMERICAN EXPRESS` to the same `ONE_OF` list only if you want to catch every variant.

A rule that never matches is not reported as an error: the condition set is skipped and the payment falls through to your next condition set or the default route.
</Warning>

<Note>
**Co-badged cards.** A card carrying two schemes can resolve to a composite label such as `ELO/DISCOVER` or `JCBRUPAY`, which matches neither component on its own. If you route co-badged traffic, confirm the resolved label with a real card before relying on the rule.
</Note>

#### Confirming a brand value

The same method the `CARD_ISSUER_COUNTRY` section below uses applies to `CARD_BRAND`:

1. Submit a payment in sandbox with the card you want to route.
2. Read `card_data.brand` from the payment (payment details in the dashboard, or the [Retrieve Payment](/reference/payments/retrieve-payment-by-id) response).
3. Build the rule against that exact value.

#### Testing `CARD_ISSUER_COUNTRY` rules in sandbox

<Warning>
**Provider test-card countries are simulator metadata**

The "country" a payment provider documents for its test cards exists only inside that provider's own test environment — it is simulator metadata attached to the PAN, not a property of the number itself. Yuno's BIN lookup resolves the real-world registry entry instead, so a test card's documented country and its resolved `card_data.country_code` in Yuno usually differ.
</Warning>

Two examples with Stripe's test cards:

| Test card | Documented by the provider as | Resolves in Yuno as | Why |
|---|---|---|---|
| `4242 4242 4242 4242` | US | `GB` (issuer: Stripe Payments UK) | BIN `424242` is registered to Stripe Payments UK Ltd in the actual Visa registry |
| `4000 0019 6000 0008` | Cyprus | `US` | Any `4000 00...` Stripe test card resolves the same `400000` registry record, which is a US-registered range, regardless of the country the last digits encode |

To verify a `CARD_ISSUER_COUNTRY` rule end-to-end today, work with resolved values rather than documented ones — the lookup is deterministic:

1. Run one sandbox payment with a candidate test card.
2. Read `card_data.country_code` from the payment (payment details in the dashboard, or the [Retrieve Payment](/reference/payments/retrieve-payment-by-id) response).
3. Build the rule against that value. For example, `4242 4242 4242 4242` is a dependable `GB` card end-to-end.

The same caveat applies to every BIN-derived condition (`CARD_TYPE`, `CARD_BRAND`), though country is where provider test-card documentation diverges most often.
