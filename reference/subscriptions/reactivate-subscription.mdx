---
title: "Reactivate Subscription"
openapi: "/openapi/subscriptions/reactivate-subscription.json POST /subscriptions/{subscription_id}/reactivate"
description: "Returns a canceled or completed subscription to ACTIVE, keeping the same subscription and history."
---

Use this endpoint for win-back campaigns. Calling it returns a `CANCELED` or `COMPLETED`
subscription to `ACTIVE` — or to `TRIALING` when a trial phase covers the reactivated cycle —
keeping the same `id` and its full payment history. No successor subscription is ever created
and `previous_subscription_id` is never set by this call. No charge is made on the call itself.

<Note>
**Allowlisted organizations only**

Reactivation is gated per organization, and this is checked before the subscription's status. If
your calls return `409` `"Subscription reactivation is not enabled for this organization"`,
contact your Yuno representative to have it enabled.
</Note>

## Which subscriptions can be reactivated

| Current `status` | Result |
| --- | --- |
| `CANCELED` | Reactivated. |
| `COMPLETED` | Reactivated, if billing cycles remain — see [When the billing cycles are used up](#when-the-billing-cycles-are-used-up) below. |
| Any other status | `409` `INVALID_SUBSCRIPTION_STATUS`, naming the current status in `current_status`. A `PAUSED` subscription is resumed with [Resume Subscription](/reference/subscriptions/resume-subscription) instead. |

```json 409 — status is not CANCELED or COMPLETED
{
  "code": "INVALID_SUBSCRIPTION_STATUS",
  "messages": [
    "Only a CANCELED or COMPLETED subscription can be reactivated."
  ],
  "current_status": "ACTIVE"
}
```

A subscription whose `availability.finish_at` has already passed is refused with `400`
`INVALID_DATE`, whatever its status:

```json 400 — availability window already closed
{
  "code": "INVALID_DATE",
  "messages": [
    "The subscription can not be resume due to a conflict with the availability dates. Please update availability dates and try again if you want to keep using the subscription"
  ]
}
```

## When the billing cycles are used up

A `COMPLETED` subscription that used every cycle in `billing_cycles.total` is refused with `409`
`INVALID_SUBSCRIPTION_STATUS`:

```json 409 — no billing cycles left
{
  "code": "INVALID_SUBSCRIPTION_STATUS",
  "messages": [
    "The subscription exhausted its 1 billing cycles. Send billing_cycles.total greater than 1 in the reactivate body."
  ],
  "current_status": "COMPLETED"
}
```

Send `billing_cycles.total` with a value higher than the current one to raise the limit and
reactivate in the same call. This does not create a successor — it raises the limit **on the same
subscription**, keeping its `id` and history intact:

```json Raise the limit and reactivate
{
  "billing_cycles": { "total": 24 }
}
```

Sending `billing_cycles.total`:

| Condition | Result |
| --- | --- |
| Not greater than the current total | `400` `BAD_REQUEST` — `"billing_cycles.total must be greater than the current total (N)."` |
| The subscription has no billing cycle limit at all | `400` `BAD_REQUEST` — `"billing_cycles.total cannot be set on a subscription without a billing cycle limit."` |
| Not a positive integer | `400` `BAD_REQUEST` — `"billing_cycles.total must be a positive integer."` |

Sending `billing_cycles.total` for a subscription that still has cycles left is accepted the same
way: it raises the limit, it is not restricted to exhausted subscriptions. An explicit
`billing_cycles.total: null` is treated the same as omitting the field — the current total is left
unchanged.

## Choosing the next billing date

`billing_cycle_behavior` is the same axis used on resume and on plan changes.

<CodeGroup>
```json KEEP (default, or omitted)
{ "billing_cycle_behavior": "KEEP" }

// billing_cycles.next_at -> unchanged while it is still in the future,
// otherwise rolled forward to its next future occurrence
```

```json RESTART
{ "billing_cycle_behavior": "RESTART" }

// billing_cycles.next_at -> the reactivation instant plus the subscription's frequency
// frequency.monthly_billing_day -> stamped to the day of the reactivation,
// on a monthly subscription that had none
```
</CodeGroup>

No charge is made on the call either way. An invalid value returns `400` `BAD_REQUEST` —
`"billing_cycle_behavior must be one of KEEP, RESTART."` Reactivate has no gateway-side validation
of its own: the same text comes back unchanged through the gateway.

<Note>
**RESTART and the monthly billing day**

On a monthly subscription that had no `frequency.monthly_billing_day` set, `RESTART` stamps it to
the day of the reactivation — the same rule Update Subscription and Resume Subscription apply. A
subscription that already declares a billing day keeps it.
</Note>

## The payment method

The vaulted payment method is revalidated before the subscription is reactivated. If it is no
longer enrolled, the call returns `400` `PAYMENT_METHOD_STATUS_INVALID` and the subscription stays
in its prior status:

```json 400 — payment method no longer enrolled
{
  "code": "PAYMENT_METHOD_STATUS_INVALID",
  "messages": [
    "The payment method is a state that does not allow payments to be made."
  ]
}
```

## What reactivation clears

Reactivating a subscription clears:

- `cancellation_time`
- `cancellation_source`
- `ending_time`
- `reason`
- any scheduled cancellation (`cancel_scheduled`)
- any pause that was scheduled to end on its own — a reactivated subscription never carries
  `pause_until`

The `subscription.reactivate` webhook fires once, carrying the reactivated subscription.

## Errors

<div className="code-nowrap-table dense-table">

| HTTP | `code` | When |
|---|---|---|
| `409` | `INVALID_SUBSCRIPTION_STATUS` | Reactivation is not enabled for the organization. |
| `409` | `INVALID_SUBSCRIPTION_STATUS` | The subscription's status is not `CANCELED` or `COMPLETED`. |
| `409` | `INVALID_SUBSCRIPTION_STATUS` | The subscription used up every billing cycle in `billing_cycles.total` and the request did not raise it. |
| `400` | `INVALID_DATE` | `availability.finish_at` has already passed. |
| `400` | `BAD_REQUEST` | `billing_cycles.total` is not greater than the current total, is sent on a subscription with no cycle limit, or is not a positive integer. |
| `400` | `BAD_REQUEST` | `billing_cycle_behavior` is not `KEEP` or `RESTART`. |
| `400` | `BAD_REQUEST` | An unrecognized top-level key, caught by the gateway's own JSON binding before the call reaches the engine — `"Bad request"` |
| `400` | `BAD_REQUEST` | A key other than `total` inside `billing_cycles`, forwarded raw to the engine and refused there — `"Unknown field(s): foo."` |
| `400` | `PAYMENT_METHOD_STATUS_INVALID` | The vaulted payment method is no longer enrolled. |
| `400` | `OPERATION_IN_PROCESS` | Another write against the same subscription is still in progress — `"Operation over the same subscription is already in process. Try again in a few seconds."` |

</div>
