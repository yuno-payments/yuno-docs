---
title: "Create Subscription"
openapi: "/openapi/subscriptions/create-subscription.json POST /subscriptions"
description: "Creates a recurring subscription plan with billing cycles, trial periods, and stored payment credentials."
---

<Note>
**Creating the subscription together with its first payment**

This endpoint starts a subscription from a `vaulted_token` you already hold. If the customer is signing up and paying at the same time, you can instead send a `subscription` block on [Create Payment](/reference/payments/create-payment) — one call charges the card and creates the subscription from that same charge. That route is documented for frictionless card payments only. See [Start a subscription with the first payment](/docs/payment-features/subscriptions/start-with-payment).
</Note>

<Note>
**Applying a promotion when the subscription is created**

Send `promotion` with an `id` or a `code` to apply a promotion that is attached to the plan. The first charge carries the discount. The subscription must be on a plan that has the promotion attached. The subscription stores its own copy of the promotion, which is not edited afterwards. See [Promotions on subscription plans](/docs/payment-features/subscriptions/promotions).

```json
{ "promotion": { "id": "8f2d6c1e-3b7a-4c55-9a1e-2f4d8b7c6a10" } }
```

An `AUTOMATIC` promotion attached to the plan applies on its own when the subscription is created on that plan. If the request also sends a `promotion`, the larger discount wins; the two do not stack.
</Note>

<Warning>
**Subscription Completion**

The fields `billing_cycles` and `availability.finish_at` have an impact on each other. If both are completed during the subscription creation, it will transition to the `COMPLETED` state upon reaching the nearest event defined in these fields, whether it is the billing cycle or the corresponding `finish_at`.
</Warning>

<Warning>
**Credential Usage for Previous CIT**

If you create a CIT payment (e.g. Apple Pay or card) *before* creating the subscription and pass the resulting vaulted token into the subscription, you **must** include `payment_method.card.usage` to indicate whether this is the first or a subsequent use. Without this, rebills will be treated as CITs and declined by the provider.

Required payload for new subscriptions:

```json
{
  "payment_method": {
    "type": "CARD",
    "vaulted_token": "{{vaulted_token}}",
    "card": {
      "usage": "USED"
    }
  }
}
```
</Warning>

## Promotion errors

Creating a subscription with `promotion` can fail with the codes below. In each case, nothing is created.

| HTTP | `code` | When |
| :--- | :----- | :--- |
| `404` | `PROMOTION_NOT_FOUND` | The `promotion` ID or code is unknown, or belongs to another account. |
| `422` | `PROMOTION_NOT_ATTACHED_TO_PLAN` | The promotion is not attached to the plan. |
| `422` | `PROMOTION_NOT_APPLICABLE` | The promotion cannot be applied. The `reason` says why, for example `USAGE_LIMIT_REACHED`, `EXPIRED`, or `PROMOTIONS_NOT_ENABLED` when promotions are not turned on for your organization. |
| `503` | `PROMOTION_ENGINE_UNAVAILABLE` | The promotions service did not respond. Retry the request. |
| `504` | `PROMOTION_ENGINE_TIMEOUT` | The promotions service did not respond in time. Retry the request. |

An `AUTOMATIC` promotion attached to the plan is handled differently. If it cannot be applied, because it is disabled, expired, or has no uses left, the subscription is created without it, and the request still succeeds. The same happens when the promotions service does not find the attached promotion. Only a `503` or `504` stops the creation.

Refer to the [HTTP Response Codes](/reference/getting-started/response-codes) section for details on possible error outcomes.
