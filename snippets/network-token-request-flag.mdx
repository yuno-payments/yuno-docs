The optional boolean `payment_method.network_token` lets you decide, per card, whether Yuno uses a network token. Send it on [Create Payment](/reference/payments/create-payment) and on card enrollment ([Checkout flow](/reference/payment-methods-checkout/enroll-payment-method-checkout) and [Direct API](/reference/payment-methods-direct-workflow/enroll-payment-method-api)).

| `payment_method.network_token` | Payment | Card enrollment |
| --- | --- | --- |
| `false` | Yuno never requests or reuses a network token: the PAN goes to the provider, even when the route has the network token toggle on. A token already stored for the card is kept, not deleted. | Yuno does not provision a network token for the card, including the migration path for cards enrolled without CVV. |
| `true` | On a vaulted card (`vaulted_token`, or `vault_on_success: true`), Yuno uses the card's network token, or provisions one, even when the route has the network token toggle off. | Yuno provisions a network token for the card, as it does today. |
| Omitted | The route decides, as today: the network token is used only when the route has the toggle on. | Yuno provisions a network token as today. |

The field is gated by network token onboarding: `true` only has an effect when your organization is onboarded to network tokens for the card's network and the provider supports them. When it is not, the request does not fail; the payment goes with the PAN.

The field has no effect on:

- Guest (non-vaulted) cards, which never get a network token.
- Wallet payments (Apple Pay, Google Pay, Samsung Pay).
- Network tokens you send yourself with their cryptogram (merchant external network tokens).
